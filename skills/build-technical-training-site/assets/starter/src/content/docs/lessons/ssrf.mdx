## 引导问题：谁真正发出了请求？

一个“根据 URL 生成图片预览”的接口接收 `http://127.0.0.1:PORT/private`。浏览器只把这个字符串发给应用；应用服务器随后连接目标地址。目标服务看到的来源、可达网络和身份权限都属于应用服务器。这条身份与网络边界的转移构成理解服务端请求伪造（Server-Side Request Forgery，SSRF）的起点。

OWASP 将 SSRF 描述为利用服务端应用访问非预期位置的行为；PortSwigger 进一步说明，内部系统经常依赖网络位置形成隐含信任。（来源：[OWASP](#source-owasp-ssrf-cheat-sheet)、[PortSwigger](#source-portswigger-ssrf)）

## 机制：从字符串到实际连接

1. **输入进入取回功能。** 用户影响头像抓取、Webhook、文档渲染或 URL 预览的目标。
2. **URL 被解析。** 协议、主机、端口、用户名段和编码共同影响解析结果。
3. **主机被解析为地址。** 一个域名可能得到多个地址，解析结果也可能变化。
4. **HTTP 客户端建立连接。** 自动重定向可能把已允许的初始目标带到私有地址。
5. **响应被应用使用。** 正文回显会直接暴露数据；状态码、响应时延和带外交互也可能泄露结果。

成立条件可以写成一条检查链：**服务端发起请求 + 用户影响目标 + 目标约束不足 + 服务器拥有有价值的可达性或身份**。影响取决于服务端可访问的资源，包括内部管理接口、环回服务和云实例元数据。

<Callout variant="warning" title="字符串黑名单的边界">
仅搜索 `127.0.0.1` 无法覆盖其他地址表示、DNS 解析、多地址结果和重定向。生产控制需要在规范化、解析、连接与网络出口多个位置保持一致约束。
</Callout>

## localhost 最小实验

实验脚本只在 `127.0.0.1` 的随机端口启动临时 HTTP 服务。它先展示未经约束的服务端取回，再让实验校验器拒绝私有 IPv4 地址。该校验器用于讲解第一层边界，生产系统还需要域名允许列表、连接绑定、出口控制、超时与响应限制。

运行环境：Node.js 22.12 或更高版本。

```bash
node examples/ssrf-local-lab.mjs
```

预期输出：

```text
脆弱流程：training-secret
安全流程：已阻止私有地址
```

实验检查：把脚本中的目标改成另一个 `127.0.0.1` 端口，确认安全流程继续阻止；随后阅读 `guardedFetch`，指出它仍未处理的域名解析与 IPv6 边界。

## 常见错误与边界

- **把 URL 解析当成字符串搜索。** 不同解析器、编码和地址形式会产生差异。
- **只校验域名。** 最终连接地址、全部解析结果和后续重定向也需要约束。
- **允许任意重定向。** 每一跳都会引入新的目标。
- **让应用拥有宽泛网络与身份权限。** SSRF 的影响会随服务器权限扩大。
- **忽略响应资源限制。** 大响应、慢响应和非预期内容类型会引入资源消耗与解析风险。
