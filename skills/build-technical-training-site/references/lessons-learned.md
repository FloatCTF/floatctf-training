# 交付教训与硬规则

来源：FloatCTF 培训站 `ai-literacy` 专题的外部审计与用户视觉反馈（2026-07）。  
用途：每次 `add-topic` / `refresh-topic` / `validate-site` 在写作与交付前完整执行。  
目标：阻止“过 validate 但难看、过简、事实虚标、交互凑数”的交付。

## 目录

- 根因分类
- 用户讲义与事实分层
- 证据与 researchStatus
- 排版与组件
- 动效与交互选型
- 内容深度
- 文案
- 交付前自检
- 禁止清单

## 根因分类

| 类型 | 含义 | 例子 |
| --- | --- | --- |
| 执行偷懒 | Skill 已要求，交付时跳过 | 不核验官方文档、不刷新 QA、不自查版式 |
| 门禁真空 | schema 绿 ≠ 质量够 | claim 绑错论文仍通过；过期 browser-report 不 fail |
| 组件/平台坑 | 第三方 CSS 破坏布局 | Starlight 把 `table` 设为 `display:block` 导致半宽表 |
| 交互凑数 | 有动画但无教学收益 | 给顺序列表加播放条，难概念仍纯文字 |

执行层必须先自检；Skill 层持续把可自动化项升级为门禁。

## 用户讲义与事实分层

用户提供的 PDF、Markdown、旧 HTML **只负责**：

- 章节结构与教学顺序
- 例子、类比、练习意图
- 案例叙述与课堂节奏

**不负责**：

- 产品行为是否仍当前（MCP 加载策略、CLI 命令、上下文预算）
- 论文结论是否被正确归因
- 版本号、统计、漏洞细节

硬规则：

1. 结构可跟用户材料；可过时的产品/版本断言必须打开当前官方文档核验。
2. 用户材料中的具体数字、配置、工具行为写入页面前，至少有一条独立权威来源或明确标为“示意/历史讲义数量级”。
3. 不得写“讲义里……”。页面本身就是讲义，用直接陈述。

## 证据与 researchStatus

1. 每条 MDX 中的硬主张应有 claim，且 `sourceIds` 的**语义范围**覆盖该主张。
2. 禁止凑绑定：例如用 Transformer 架构论文单独支撑“下一词预测是当代 LLM 训练目标”；用协议介绍页单独支撑某一产品的实现细节。
3. `researchStatus: complete` 默认吝啬。存在未核验产品细节时用 `partial`，并在 `notes` 写清缺口。
4. 关键机制（如长上下文中部失效）应绑定专文或等价权威来源，不能只写在正文里。
5. 用户说“先不要 commit”**不等于**跳过证据核验与视觉自检。

## 排版与组件

### 表格

1. **禁止**在 Starlight markdown 内容树中依赖原生 `<table>` 做全宽教学表。Starlight 会把 `table` 设为 `display: block`，导致表体半宽、右侧空白。
2. 教学表使用 `DataTable` 的 **CSS Grid** 实现（`not-content`），列宽 `repeat(n, minmax(0, 1fr))`，外框与内容同宽。
3. 交付前打开页面确认：表头与每一列延伸到边框右缘，无“半截表”。

### 标题装饰

1. 专题 `h3` **禁止**用短横线/`::before` 色条装饰（易出现“莫名红线”）。
2. `h2` 可用 section 编号眉题；`h3` 用字号与间距建立层级即可。

### 对照组件

1. `CodeCompare` 默认 VULNERABLE/GUARDED 仅用于安全脆弱/修复对照。
2. 非安全对照必须 `tone="neutral"`，或自定义 badge（如 VERBOSE/COMPACT、BEFORE/AFTER）。
3. 禁止把“低效文案 vs 高效文案”画成漏洞红绿框。

### 演示结果

1. 可运行示例若用于建立直觉，页面应**直接展示结果**（表格、概率条、静态输出），而不是只给 `node examples/...` 命令块。
2. 命令可作补充，不能作为唯一呈现。

## 动效与交互选型

1. 先问：这个交互是否降低理解成本？若删掉播放条后信息不变，则**不要做动画**。
2. 顺序罗列、能力演进、步骤清单优先用静态 `StepList` 或表格，不用 `ProcessTimeline` 播放控件。
3. 交互预算优先投向高理解成本关系：
   - 注意力 / O(n²) / 位置偏差
   - 上下文预算构成
   - 攻防数据流、状态机、参数变化
4. 禁止为“看起来高级”给低难度顺序知识加播放/重置/进度条。
5. 默认 `motionLevel`：通识说明优先 `static` 或 `subtle`；只有机制必须动态演示时才升到 `explanatory`/`simulation`。

## 内容深度

1. “按 PDF/讲义做一页”指**覆盖论点与关键例子**，不是压缩成摘要条。
2. 交付前对照参考材料做覆盖检查：
   - 每个主章节是否有对应网页落点
   - 每个关键例子/代码是否保留或等价转译
   - 每个图示：保留 / 转译 / 压缩 / 删除，删除须有理由
3. 单页目标过多时：
   - 拆多专题，或
   - lesson plan 写 `segments`（模块、分钟、目标、核心/拓展）
4. 练习必须能验收：对应学习目标、可观察产出；需要时给参考方向。开放题不能只有一句话口号。

## 文案

1. 遵循 nofluff：禁假对立、空比喻、情绪夸大、无信息修饰。
2. 少用“不是 X 而是 Y”，除非 X 是读者真实误解。
3. 页面是课程正文，不用“讲义里写到”“本节课我们会”等元叙述堆砌。
4. 术语首次出现给定义。

## 交付前自检（强制，交付前逐项打勾）

在告诉用户“做好了”之前，用浏览器或构建产物完成：

1. **表格**：每个教学表全宽，无半截空白。
2. **标题**：无多余装饰线、无错位编号。
3. **组件语义**：对照框标签与主题匹配。
4. **演示**：结果在页内可见，不只命令。
5. **动效**：无教学价值的播放条已删除。
6. **文案**：无“讲义里”、无堆叠假对立。
7. **事实**：产品/版本相关句已核验或标 partial。
8. **QA**：`qa-report.json` 与当前 catalog/专题一致；有浏览器能力时更新本专题路径的 browser 证据。
9. **用户未要求 commit 时**：仍完成 1–8；仅跳过 git。

用户挑出版式问题视为交付失败信号：先修根因与 Skill 规则，再改单页。

## 禁止清单

- 用用户 PDF 当唯一事实源并标 `researchStatus: complete`
- 为过 validate 而乱绑 sourceIds
- 原生 `<table>` 做 Starlight 正文全宽表
- 非安全场景硬套 VULNERABLE/GUARDED
- 顺序列表套 ProcessTimeline 播放条
- 只放 shell 命令、不展示示例输出
- 页面正文写“讲义里……”
- 过期 qa-report / browser-report 仍声称专题已验收
- 等用户截图才发现半宽表、废动画、空演示

## 与校验器的关系

当前 `npm run validate` 主要保证结构与引用图。下列项**不能**仅靠 validate 证明：

- 版式是否难看
- claim 语义是否匹配
- 动效是否有教学价值
- 内容相对参考材料是否过简

这些依赖本文件的执行纪律；能自动化的项应逐步写入 `scripts/validate-content.mjs`（例如 QA 新鲜度、scrollReveal 计数、禁止 table display 回归）。
