## 引导问题：只有一句 segmentation fault

<CodeFile file="labs/c-debugging-memory-errors/crash.c" />

<TerminalSession
  title="打印了两行，然后崩溃"
  steps={[
    { cmd: 'cd ~/lab/c' },
    { cmd: 'gcc -g crash.c -o crash', note: '多了一个 -g，稍后解释。' },
    { cmd: './crash', out: 'hello, alice (5)\nhello, bob (3)\nzsh: segmentation fault  ./crash' },
  ]}
/>

Python 出错时会给一份 Traceback，写明哪个文件、哪一行、经过了哪些函数。C 程序崩溃时，系统只告诉你一个信号的名字。

哪一行崩的？当时各个变量是多少？是谁把错误的值传进来的？二十行的程序还能靠眼睛看，两千行就不行了。这一课让 C 程序也交出它的「Traceback」。

## 一、用 gdb 找到崩溃的位置

### 1. 准备

**gdb** 是调试器：它替你运行程序，可以让程序在任何地方停下，然后查看当时的一切。Kali 默认没有装它：

<TerminalSession
  replay="skip"
  title="安装（只需一次）"
  steps={[
    { cmd: 'sudo apt install -y gdb', note: '和第 3 课装 htop 的方法一样。' },
  ]}
/>

<TerminalSession
  title="确认装好了"
  steps={[
    { cmd: 'gdb --version | head -n 1', out: 'GNU gdb (Debian 17.2-1+b1) 17.2' },
  ]}
/>

编译时的 `-g` 让 gcc 在可执行文件里多存一份**调试信息**：每条机器指令对应源文件的哪一行，每个变量叫什么名字、放在哪。有了它，gdb 才能用源码的语言和你说话。从这一课起，写程序时编译命令里都加上 `-g`。（来源：[gcc(1)](#source-man-gcc)）

### 2. 在 gdb 里运行，看调用栈

在终端里输入 `gdb -q ./crash` 进入 gdb，提示符变成 `(gdb)`。`-q` 是不显示开头那一大段版权信息。

<TerminalSession
  environment="GDB · ./crash"
  prompt="(gdb)"
  title="gdb -q ./crash 之后"
  steps={[

() from /usr/lib/x86_64-linux-gnu/libc.so.6',
      note: 'run 启动程序。它照常运行，崩溃时没有退出，而是停住了。最后一行说它停在 C 库里的某个地址。',
    },

      cmd: 'bt',
      out: '#0  0x00007ffff7f276d9 in ?? () from /usr/lib/x86_64-linux-gnu/libc.so.6\n#1  0x0000555555555161 in name_length (name=0x0) at crash.c:5\n#2  0x000055555555517b in greet (name=0x0) at crash.c:9\n#3  0x00005555555551e0 in main () at crash.c:16',
      note: 'bt 是 backtrace：此刻的调用栈。这就是 C 程序的 Traceback。',
    },
  ]}
/>

`bt` 的每一行是一个栈帧，就是第 21 课图里的那些方框。最上面的 `#0` 是崩溃发生的地方，往下依次是调用它的函数，最下面是 `main`。

<DataTable
  caption="读这四帧"
  headers={["帧", "在哪", "说明"]}
  rows={[
    ["#0", "C 库里，没有函数名", "崩溃的精确位置。这是 strlen 的内部，不是你的代码，也没有它的调试信息，所以显示 ??"],
    ["#1", "name_length，crash.c 第 5 行", "你的代码里离崩溃最近的一层。参数 name=0x0，是空指针"],
    ["#2", "greet，crash.c 第 9 行", "它调用了 name_length，传进去的 name 也是 0x0"],
    ["#3", "main，crash.c 第 16 行", "它调用了 greet"],
  ]}
  columnRatios={[0.4, 1.4, 3]}
/>

读法：**从上往下找到第一个属于你自己代码的帧，从那里开始看。** 这里是 `#1`：`strlen(name)` 收到了一个空指针。

### 3. 沿着调用栈往回找原因

`name_length` 只是把参数原样交给 `strlen`，错不在它。空指针是从哪来的？`frame` 命令可以切换到任意一帧，查看那一层的变量：

<TerminalSession
  environment="GDB · ./crash"
  prompt="(gdb)"
  title="切到 main 那一帧看变量"
  steps={[
    { cmd: 'run', out: 'Starting program: /home/kali/lab/c/crash\n[Thread debugging using libthread_db enabled]\nUsing host libthread_db library "/usr/lib/x86_64-linux-gnu/libthread_db.so.1".\nhello, alice (5)\nhello, bob (3)\n\nProgram received signal SIGSEGV, Segmentation fault.\n0x00007ffff7f276d9 in ?? () from /usr/lib/x86_64-linux-gnu/libc.so.6' },
    { cmd: 'frame 3', out: '#3  0x00005555555551e0 in main () at crash.c:16\n16\t        greet(names[i]);', note: '切到 #3，也就是 main。它显示了这一帧正停在哪一行。' },
    { cmd: 'print i', out: '$1 = 2', note: 'print 显示一个变量或表达式的值。崩溃时 i 是 2。' },
    { cmd: 'print names[i]', out: '$2 = 0x0', note: 'names[2] 是空指针。' },
    { cmd: 'print names[1]', out: '$3 = 0x55555555601a "bob"', note: '对比一下：names[1] 是一个有效的地址，gdb 顺便把它指向的字符串也显示了出来。' },
    { cmd: 'quit', out: 'A debugging session is active.\n\n\tInferior 1 [process 547] will be killed.\n\nQuit anyway? (y or n) y', note: '退出。程序还停在那里，gdb 会确认一次，回答 y。' },
  ]}
/>

原因找到了：`names` 数组的第三个元素是 `NULL`，而 `main` 的循环把三个元素都当成名字交给了 `greet`。崩溃发生在 C 库里，错误却在三层调用之外的 `main`。**出错的地方和崩溃的地方常常不是同一处**，调用栈就是连接两者的那条线。

（来源：[gdb(1)](#source-man-gdb)、[N1570](#source-n1570)）

## 二、单步执行，找逻辑错误

### 1. 不崩溃，只是算错了

<CodeFile file="labs/c-debugging-memory-errors/average.c" />

<TerminalSession
  title="四个成绩的平均分"
  steps={[
    { cmd: 'gcc -g average.c -o average' },
    { cmd: './average', out: 'average 65', note: '80、90、70、100 的平均分应当是 85。' },
  ]}
/>

程序没有崩溃，没有警告，只是答案不对。这种错误 `bt` 帮不上忙，需要让程序一步一步地走，边走边看变量。

### 2. 断点和单步

    { cmd: 'next', out: '5\t    for (int i = 1; i < count; i++) {', note: '第 6 行执行完了，回到 for 那一行。现在看看变量。' },
    { cmd: 'print i', out: '$1 = 1' },
    { cmd: 'print sum', out: '$2 = 90', note: '循环体只执行了一次，sum 却是 90，而第一个成绩是 80。' },

    { cmd: 'info locals', out: 'i = 1\nsum = 90', note: 'info locals 一次列出当前函数的所有局部变量。' },
    { cmd: 'continue', out: 'Continuing.\naverage 65\n[Inferior 1 (process 3363) exited normally]', note: 'continue 让程序继续运行，直到下一个断点或结束。' },
    { cmd: 'quit' },
  ]}
/>

第一圈循环时 `i` 是 1，不是 0。`values[0]` 被跳过了。回头看第 5 行：`int i = 1`。

把 `1` 改成 `0`，重新编译：

<TerminalSession
  title="改完再试"
  steps={[
    { cmd: 'gcc -g average.c -o average', setup: "sed -i 's/int i = 1/int i = 0/' average.c" },
    { cmd: './average', out: 'average 85' },
  ]}
/>

这个 bug 光看代码也能发现。gdb 的价值在于：你不必猜。怀疑哪里就停在哪里，看变量的实际值和你以为的值差在哪。

## 三、不崩溃的错误，和一张对照表

### 1. 多写了一个，程序若无其事

<CodeFile file="labs/c-debugging-memory-errors/fill.c" mark="5-6" note="申请了 4 个 int，循环却写了 5 次。" />

<TerminalSession
  title="没有任何异常"
  steps={[
    { cmd: 'gcc -Wall fill.c -o fill', setup: 'cp ~/lab/python/average.c . && gcc -g average.c -o average', note: '没有警告。' },
    { cmd: './fill', out: '9', note: '结果正确，没有崩溃。' },
  ]}
/>

`squares[4]` 写到了申请的那块内存之外。这次没出事，只是因为那 4 个字节后面碰巧没有别人在用。这是最危险的一种错误：它不崩溃，gdb 无处可停；它也不总是算错，测试发现不了。等程序变大，那几个字节后面住进了别的数据，它才发作，而且发作在离这里很远的地方。

第 22、24 课用过的 AddressSanitizer 就是对付它的：

<TerminalSession
  title="同一个程序，换个编译选项"

边界：gdb 只在程序实际运行到的地方有用，AddressSanitizer 只报告实际发生了的越界。一段有问题的代码如果这次没被执行到，两者都不会发现它。它们是帮你定位问题的工具，不能证明程序没有问题。

<KeyTakeaway>
用 `-g` 编译之后，gdb 可以把崩溃还原成一条带行号和参数的调用栈：`run` 让程序停在出事的那一刻，`bt` 列出调用链，从上往下找到第一个属于自己代码的帧，再用 `frame` 和 `print` 沿着它往回找到错误的来源。逻辑错误用断点和单步来查。不崩溃的内存错误交给 `-fsanitize=address`。排查的顺序是：先读警告，再开检测，最后上调试器。
</KeyTakeaway>
