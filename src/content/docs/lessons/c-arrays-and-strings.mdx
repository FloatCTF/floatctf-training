## 一、数组：一排连续的格子

### 1. 声明和使用

<CodeFile file="labs/c-arrays-and-strings/array.c" />

<TerminalSession

    { cmd: 'gcc -Wall array.c -o array' },

`int ports[4]` 的意思是：四个 `int`，在内存里紧挨着放。下标从 0 开始，和 Python 一样。

和 Python 的列表有三点不同：

  caption="C 的数组和 Python 的列表"
  headers={["", "Python 列表", "C 数组"]}
  rows={[
    ["长度", "随时可以 append，len() 能问到", "声明时定死，之后不能变；数组自己不记录长度"],
    ["元素类型", "可以混放", "全部是同一种类型"],
    ["越界", "IndexError，程序停下", "不检查。读到或改到的是旁边的内存"],
  ]}

/>

`sizeof(ports) / sizeof(ports[0])` 是算元素个数的惯用写法：总字节数除以一个元素的字节数。它只在声明数组的那个函数里管用；把数组传给别的函数时，长度要另外作为参数传过去。

### 2. 越界：读到了邻居

回到引导问题。逐行执行，留意 `codes` 和 `i` 的地址：

<CodeStepper
  client:visible
  trace={oobTrace}
  view="memory"
  title="codes[3] 读到的是谁"
  eyebrow="STEP THROUGH / C 的内存"
  intro="codes 的三个格子占着 …ec10 到 …ec1b。再往后 4 个字节是什么？"
/>

`codes[3]` 对编译器来说只是一道算术题：从 `codes` 的开头往后数 3 个 `int`，取那里的 4 个字节。它不管那里还是不是数组的一部分。在这次运行里，那个位置放的恰好是循环变量 `i`，而此刻 `i` 等于 3。

换一个编译器、换一组编译选项，变量的摆放可能不同，读到的就是别的东西。标准把越界访问定为**未定义行为**，程序此后的任何表现都不可信。（来源：[N1570](#source-n1570)、[Beej's Guide: Arrays](#source-beej-arrays)）

<Callout variant="warning" title="越界写比越界读更糟">
这个例子是越界读，结果只是多打了一个数。如果是越界写，`codes[3] = 0;`，被悄悄改掉的就是 `i`，循环会因此乱掉。程序往往在很久以后、在毫不相干的地方才出问题，非常难查。
</Callout>

## 二、字符串：以空字符结尾的 char 数组

### 1. 字符串的真面目

C 没有专门的字符串类型。字符串就是一个 `char` 数组，外加一个约定：**在最后一个字符后面放一个值为 0 的字节，表示到此结束。** 这个字节写作 `'\0'`，叫空字符。（来源：[N1570](#source-n1570)、[CS50x: Lecture 2](#source-cs50-arrays)）

<CodeFile file="labs/c-arrays-and-strings/str.c" />

<TerminalSession
  title="四个字母，五个字节"
  steps={[
    { cmd: 'gcc -Wall str.c -o str' },
    { cmd: './str', out: 'kali\n5 4\nKali\nK=75 a=97 l=108 i=105', note: '第二行：sizeof 是 5，strlen 是 4。差的那一个就是结尾的空字符。' },
  ]}
/>

<DataTable
  caption="两种「长度」"
  headers={["写法", "量的是什么", "对 char name[] = \"kali\""]}
  rows={[
    ["sizeof(name)", "数组占了多少字节，包括结尾的空字符", "5"],
    ["strlen(name)", "从头数到空字符之前有几个字符", "4"],
  ]}
  columnRatios={[1, 2.6, 1.4]}

字符串的每个元素是一个 `char`，可以像数组那样用下标读写。第 14 行的循环条件 `name[i] != '\0'` 是处理字符串的标准写法：一直走到空字符为止。（来源：[strlen(3)](#source-man-strlen3)）

### 2. 结尾标记决定一切

<CodeStepper

  eyebrow="STEP THROUGH / C 的内存"
  intro="buf 的 8 个格子画成了一排。看 '\0' 的位置怎样决定 printf 打印到哪里为止。"

<TerminalSession
  title="结果"
  steps={[
    { cmd: 'gcc -Wall fill.c -o fill' },
    { cmd: './fill', out: 'nc!\nn' },

/>

`printf("%s", buf)` 并不知道 `buf` 有多大。它只是从第 0 格开始一个个往外打，遇到 `'\0'` 才停。所以：

- 把中间某一格改成 `'\0'`，字符串就在那里结束，后面的内容还在内存里，只是不再被看见。
- 如果数组里**没有** `'\0'`，`printf` 会一路读过数组的末尾，把后面不相干的内存也打出来。这又是越界。

`strcpy(buf, "nc")` 把一个字符串连同结尾的空字符一起复制进 `buf`。C 里不能用 `=` 给数组整体赋值，也不能用 `==` 比较两个字符串的内容，复制用 `strcpy`，比较用 `strcmp`。这些函数都声明在 `<string.h>` 里。（来源：[Beej's Guide: Strings](#source-beej-strings)）

## 三、写过头的时候

### 1. strcpy 不知道目的地有多大

<CodeFile file="labs/c-arrays-and-strings/smash.c" mark="6" note="buf 只有 8 个字节，要复制进去的字符串连同结尾有 28 个字节。" />

<TerminalSession
  title="编译器先提醒了一次"
  steps={[
    {
      cmd: 'gcc smash.c -o smash',
      out: 'smash.c: In function ‘main’:\nsmash.c:6:5: warning: ‘__builtin_memcpy’ writing 28 bytes into a region of size 8 overflows the destination [-Wstringop-overflow=]\n    6 |     strcpy(buf, "this string is far too long");\n      |     ^~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~\nsmash.c:5:10: note: destination object ‘buf’ of size 8\n    5 |     char buf[8];\n      |          ^~~',
      note: '这次两边的大小在编译时都看得出来，所以 gcc 发现了：要把 28 个字节写进 8 个字节的地方。它只是警告，照样生成了可执行文件。',
    },
    { cmd: './smash', out: 'this string is far too long\nzsh: segmentation fault  ./smash', note: '先把整句话打印了出来，然后才崩溃。' },
  ]}
/>

`strcpy` 只拿到了 `buf` 的起始地址，不知道它有多大。它从那里开始一个字节一个字节地写，写满 8 个之后继续往后写了 20 个。保证目的地够大，是调用者的责任。（来源：[strcpy(3)](#source-man-strcpy3)）

多出来的 20 个字节写到了哪里？上一课讲过，`buf` 在 `main` 的栈帧里。栈帧里除了局部变量，还存着一些让函数能正常返回的信息，例如「返回之后回到哪里继续执行」。它们就在局部变量的后面，被这 20 个字节盖掉了。

所以程序是这样走的：`strcpy` 写坏了栈帧，但 `buf` 开头的内容是完好的，`printf` 正常打印；等到 `main` 执行 `return`，要用到那份已经被盖掉的信息，程序跳到了一个无效的地方，系统把它终止。**出错的那一行和崩溃的那一行，不是同一行。**

这种错误叫**缓冲区溢出**。下学期会专门研究它，现在只需要知道它是怎么发生的。

### 2. 两道额外的防线

编译时加上 `-fstack-protector-strong`，编译器会在栈帧里放一个哨兵值，函数返回前检查它有没有被改动：

<TerminalSession
  title="让程序自己发现栈被写坏了"
  steps={[
    { cmd: 'gcc -fstack-protector-strong smash.c -o smash', out: '…（和上面相同的警告）\n      |          ^~~' },
    { cmd: './smash', out: 'this string is far too long\n*** stack smashing detected ***: terminated\nzsh: abort  ./smash', note: '程序在返回之前发现哨兵值变了，主动终止，并说明了原因。' },
    { cmd: 'echo $?', out: '134', note: '128 加 6。6 是 abort 这个信号的编号。' },
  ]}
/>

另一个工具是第 26 课要细讲的 AddressSanitizer。用它重新编译引导问题里的 `oob.c`：

<TerminalSession
  title="越界的那一刻就报告"

      note: '这次没有打印出 3。程序在第四次读取时被拦下，报告指出：oob.c 第 6 行，越界读了变量 codes。地址和进程号每次不同。',

### 3. 读入一行的正确写法

字符串溢出最常见的来源是读输入：你不知道用户会敲多长。`fgets` 要求你告诉它缓冲区有多大，它绝不多写。

<CodeFile file="labs/c-arrays-and-strings/name.c" mark="7-8" />

<TerminalSession
  title="输入比缓冲区长也不会出事"
  steps={[
    { cmd: 'gcc -Wall name.c -o name' },
    { cmd: './name', stdin: ['kali'], out: 'name: kali\nhello, kali (4)' },
    { cmd: './name', stdin: ['administrator'], out: 'name: administrator\nhello, adminis (7)', note: 'name 只有 8 个字节。fgets 最多读 7 个字符，留一个位置放空字符，多出来的部分没有读进来。' },
  ]}
/>

第 8 行 `name[strcspn(name, "\n")] = '\0';` 是去掉末尾换行的惯用写法：`fgets` 会把你按的回车也读进来，这一行把它换成空字符。

<Callout variant="danger" title="永远不要用 gets">
老教程里常见的 `gets(buf)` 不接受缓冲区的大小，用户输入多长它就写多长，必然溢出。它的手册页第一句话就是「永远不要使用这个函数」。读入一行一律用 `fgets`。
</Callout>

（来源：[fgets(3)](#source-man-fgets3)、[gets(3)](#source-man-gets3)）

<KeyTakeaway>
数组是内存里连着的一排同类型的格子，它不记录自己的长度，C 也不检查下标：越界读到的是旁边的变量，越界写会悄悄改掉它们。字符串是以空字符 `'\0'` 结尾的 `char` 数组，一切处理字符串的函数都靠这个结尾标记判断长度。往数组里写的内容超过它的大小，会盖掉栈帧里的其他东西，程序通常在函数返回时崩溃。读输入用 `fgets` 并给出缓冲区大小。
</KeyTakeaway>
