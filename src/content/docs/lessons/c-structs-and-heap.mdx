## 引导问题：这块内存该放在哪

假设要写一个函数，读入若干个成绩，返回给调用者。有两个麻烦：

- 有多少个成绩，要到程序运行时才知道。数组的长度却得在写代码时定下来。
- 函数里的局部数组，在函数返回时就消失了。上一课讲过，把它的地址交出去是悬垂指针。

需要的是这样一块内存：**大小在运行时决定，并且不随函数返回而消失。** 栈帧给不了。这一课去另一个地方要。

## 一、结构体：把几样东西捆在一起

规则只有一条：**手里是结构体本身，用点；手里是指向它的指针，用箭头。**（来源：[Beej's Guide: Structs](#source-beej-structs)）

`promote(&alice)` 传的是地址。和上一课的 `swap` 一样，函数要改调用者的变量，就得拿到它的地址。结构体往往比较大，即使不修改，传地址也比复制一整份省事，所以结构体几乎总是通过指针传递。

### 2. 结构体有多大

通常是各成员大小之和，但不总是。编译器有时会在成员之间留几个空字节，让每个成员都落在合适的地址上，这叫填充。例如 `struct { char c; int n; }` 在这台机器上占 8 个字节，而不是 5 个。需要知道大小时永远用 `sizeof`，不要自己加。（来源：[N1570](#source-n1570)）

### 2. 堆块不随函数返回而消失

回到引导问题的第二个麻烦。在函数里申请堆内存，把地址返回给调用者：

    { cmd: './make_user', out: 'bob 1' },

这是上一课 `dangling.c` 的正确写法。两者都返回了一个地址，区别在于那个地址指向哪里：栈帧里的局部变量随函数返回而作废，堆块要等到 `free` 才作废。

随之而来的是责任：`new_user` 申请了内存却没有释放，它把这个责任连同指针一起交给了调用者。`main` 用完之后必须 `free(bob)`。谁最后拿着指针，谁负责释放。

## 三、三种内存错误

栈上的内存由系统替你管。堆上的内存由你管，于是多了三种出错的方式。它们的共同点是：**编译能通过，程序也常常「看起来」正常。**

### 1. 释放后使用

<CodeFile file="labs/c-structs-and-heap/uaf.c" mark="7-8" />

<TerminalSession
  title="free 之后还去读"
  steps={[
    {
      cmd: 'gcc -Wall uaf.c -o uaf',
      out: 'uaf.c: In function ‘main’:\nuaf.c:8:5: warning: pointer ‘score’ used after ‘free’ [-Wuse-after-free=]\n    8 |     printf("%d\\n", *score);\n      |     ^~~~~~~~~~~~~~~~~~~~~~\nuaf.c:7:5: note: call to ‘free’ here\n    7 |     free(score);\n      |     ^~~~~~~~~~~',
      note: '这个例子足够简单，编译器看出来了。真实程序里 free 和使用往往隔着好几个函数，编译器就看不出了。',
    },
    { cmd: './uaf', out: '…（一个每次运行都不同的数。采集时是 1652380725）', note: '没有崩溃，打印了一个莫名其妙的数。本来存的是 90。' },
  ]}
/>

`free` 之后，`score` 里的地址没有变，但那块内存已经还给了系统。系统可能在里面放了自己的管理信息，也可能已经把它分给了程序里别的 `malloc`。继续通过旧指针读写，读到的是别人的数据，写下去改的也是别人的数据。

### 3. 内存泄漏

<CodeFile file="labs/c-structs-and-heap/leak.c" mark="6" note="循环三次，每次申请 100 个字节，从不释放。" />

<TerminalSession
  title="申请了不还"
  steps={[
    { cmd: 'gcc -Wall leak.c -o leak' },
    { cmd: './leak', out: 'done', note: '没有任何异常。' },

/>

每一圈循环结束，`block` 这个指针变量就消失了，而它指向的堆块没有人释放，也再没有人知道它的地址。这块内存直到程序退出都被白白占着。一个运行几秒的小程序看不出问题；一个连续运行几个月的服务器程序，每处理一个请求漏一点，迟早把内存耗尽。

### 4. 让工具替你盯着

这三种错误，肉眼和编译器都靠不住。第 22 课用过的 AddressSanitizer 可以在运行时抓住它们：

<Callout variant="warning" title="这三种错误不只是 bug">
前两种错误的共同点是：程序在使用一块自己已经不拥有的内存，而那块内存里现在放的是什么，取决于程序之后又做了哪些事。下学期会看到，很多严重的安全漏洞就属于这两类。现在的目标是不写出它们，并且在它们出现时认得出来。
</Callout>

<KeyTakeaway>
结构体把相关的数据捆成一个类型，本体用点、指针用箭头访问成员。堆是栈之外的另一块内存：`malloc` 申请、`free` 归还，大小可以在运行时决定，也不随函数返回而消失，但只能通过指针访问，并且要自己负责释放。由此产生三种错误：释放后使用、重复释放、内存泄漏。它们编译时不报错，运行时常常没有症状，要靠 `-fsanitize=address` 这样的工具来发现。
</KeyTakeaway>
