## 引导问题：点开现代网站时，为什么地址栏没刷新，页面数据却变了

第 37 课的留言板提交表单后会跳回整份 `index.php`；而在常见的单页应用（SPA）后台里，打开 Network 面板往往能看到另一条请求路径：

1. 首次打开页面取回的是静态 HTML 外壳和打包好的 `.js` 脚本。
2. 登录、翻页、查资料时，前端脚本向 `/api/...` 发接口请求，拿到 JSON 后局部更新 DOM。
3. 响应头里写着 `Server: nginx`，真正执行业务的后端则是上游的 Python、Java、Go 或 Node 进程。

下面用 4 个本地文件起一个隔离在 `/tmp/modern-web-nginx` 的 Nginx 实例（不动系统 `/etc/nginx`），把这条链路跑通。

### 1. 浏览器为什么发 OPTIONS 预检，curl 却畅通无阻

并非每次跨源请求都会触发预检；而且当服务端返回 `Access-Control-Max-Age` 时，浏览器会在缓存期内复用预检结果。但只要前端跑在 `http://127.0.0.1:8088` 却直接调 `http://127.0.0.1:9000`（端口不同即**跨源**），带了 `Content-Type: application/json` 或 `Authorization` 这类非简单请求头且未命中预检缓存，浏览器就会先发 **OPTIONS 预检请求**询问来源、方法和请求头是否允许；随后的正式响应也必须带匹配的 `Access-Control-Allow-Origin`（来源：[MDN CORS](#source-mdn-cors)、[Fetch 预检规范](#source-fetch-cors)）：

<TerminalSession
  environment="KALI 终端 B"
  title="用 curl 模拟一次带请求头声明的 CORS 预检"
  steps={[
    {
      cmd: "curl --noproxy '*' -sS -i -X OPTIONS -H 'Origin: http://127.0.0.1:8088' -H 'Access-Control-Request-Method: POST' -H 'Access-Control-Request-Headers: content-type' http://127.0.0.1:9000/api/login",
      out: 'HTTP/1.1 204 No Content\nServer: BaseHTTP/0.6 Python/3.14.10\nDate: Wed, 25 Nov 2026 09:43:59 GMT\nAccess-Control-Allow-Origin: http://127.0.0.1:8088\nVary: Origin\nAccess-Control-Allow-Headers: Authorization, Content-Type\nAccess-Control-Allow-Methods: GET, POST, OPTIONS',
      note: '按 RFC 9110 §8.6，204 响应不带 Content-Length。浏览器核对完才发真正的 POST；而 curl 不遵守同源策略，所以 CORS 管不住命令行直接调接口。',
    },
  ]}
/>

回头看刚才的 Nginx 入口：前端页面和 `/api/login` 都挂在 `http://127.0.0.1:8088` 下，协议、主机、端口全相同，属于**同源**，浏览器也就不会多发这趟跨源预检。

### 2. 登录拿到 JWT，再亲手拆开验签

## 三、认证 ≠ 授权与上线配置底线

### 1. 用同一个真 Token 试出「认证」和「授权」的分界

实际项目里极常见的一类漏洞叫**失效访问控制 / 对象级越权（IDOR / BOLA）**（来源：[OWASP A01:2021](#source-owasp-a01-bac)）。很多接口只检查「Token 是不是真的」，却忘了查「这个人能不能看这条数据」。

对受保护接口 `/api/profile` 而言，完成 `alg` 白名单、签名和 `exp` 有效期校验，只是通过了**认证（Authentication，你是谁）**，还没有回答**授权（Authorization，你能否读写目标对象）**。下面依次测三条受保护资源请求：不带令牌（按 [RFC 9110](#source-rfc9110) 回 `401` 并附 `WWW-Authenticate: Bearer`，登录失败同样附质询头）、带 Alice（`uid=101`）的真 Token 查自己、再用同一把真 Token 查 Bob（`uid=102`）：

<TerminalSession
  environment="KALI 终端 B"
  title="对比：未认证 401 vs 查自己 200 vs 越权查他人 403"
  steps={[
    {
      cmd: "curl --noproxy '*' -sS -i 'http://127.0.0.1:8088/api/profile'",
      out: 'HTTP/1.1 401 Unauthorized\nServer: nginx/1.30.4\n…\nWWW-Authenticate: Bearer realm="modern-web-lab"\n\n{\n  "error": "missing Bearer token"\n}',
      note: '没带凭据或凭据无效，属于未通过认证，回 401 并用 WWW-Authenticate 说明需要 Bearer 令牌。',
    },
    {
      cmd: `curl --noproxy '*' -sS -i -H "Authorization: Bearer $TOKEN" 'http://127.0.0.1:8088/api/profile?uid=101'`,
      out: 'HTTP/1.1 200 OK\nServer: nginx/1.30.4\n…\n{\n  "uid": 101,\n  "username": "alice",\n  "role": "student",\n  "note": "Alice 的个人实验记录"\n}',
      note: 'Token 里的 uid 和查询参数都是 101，认证和授权一起通过。',
    },
    {
      cmd: `curl --noproxy '*' -sS -i -H "Authorization: Bearer $TOKEN" 'http://127.0.0.1:8088/api/profile?uid=102'`,
      out: 'HTTP/1.1 403 Forbidden\nServer: nginx/1.30.4\n…\n{\n  "error": "forbidden",\n  "detail": "authenticated as alice (uid=101), cannot read uid=102"\n}',
      note: '服务端认出了你是 Alice，但拒绝你看别人的记录，返回 403（部分线上系统为隐藏对象是否存在，也会统一回 404）。漏掉这行归属比对，改一个数字就能把全站用户资料翻个遍。',
    },
  ]}

<KeyTakeaway>
前后端分离架构常用 Nginx 统一托管静态前端并转发 JSON API：同源经反代可避开跨源预检，跨源请求由浏览器按 CORS 策略决定是否放行脚本读取。三段 JWS 形态 JWT 的前两段仅作 Base64URL 编码而非加密；服务端需依次校验 alg 白名单、签名和 exp 完成认证（失败回 401），再独立核对对象归属完成授权（失败回 403）。
</KeyTakeaway>
