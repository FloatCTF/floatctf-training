## 引导问题：你点开一个现代网站，为什么地址栏没刷新数据却变了

第 37 课的留言板里，提交表单后服务器回 303，浏览器重新请求整份 `index.php`。可在今天常见的管理后台、网盘或校内系统里，打开开发者工具的 Network 面板，你会发现：

1. 第一个请求拿回的 HTML 几乎是个空壳，外加一堆打包好的 `.js` 文件；
2. 后面每一次登录、翻页、改资料，浏览器都只向 `/api/...` 发请求，收回来的是 JSON；
3. 响应头里经常写着 `Server: nginx`，但后端明明是用 Python、Java、Go 或 Node 写的。

这一课把这套现代结构缩成 4 个本地文件，用课程专属的独立回环 Nginx 实例在 Kali 里跑起来，不改动系统 `/etc/nginx` 配置。

## 二、CORS 预检与 JWT 拆解实操

### 1. 为什么浏览器会触发 CORS 预检，而 curl 一切正常

并不是所有跨源请求都会预检，但前端页面跑在 `http://127.0.0.1:8088` 而直接调用另一个端口 `http://127.0.0.1:9000`（端口不同即**跨源**），且携带 `Content-Type: application/json` 或 `Authorization` 这类非简单请求头时，浏览器会先发一次 **OPTIONS 预检请求**，带上 `Origin`、`Access-Control-Request-Method` 和 `Access-Control-Request-Headers`，检查服务端是否同时放行来源、方法与请求头；随后的实际请求响应同样必须携带匹配的 `Access-Control-Allow-Origin`（来源：[MDN CORS](#source-mdn-cors)、[Fetch 预检规范](#source-fetch-cors)）：

<TerminalSession
  environment="KALI 终端 B"
  title="用 curl 模拟一次带请求头声明的 CORS 预检"
  steps={[
    {
      cmd: "curl --noproxy '*' -sS -i -X OPTIONS -H 'Origin: http://127.0.0.1:8088' -H 'Access-Control-Request-Method: POST' -H 'Access-Control-Request-Headers: content-type' http://127.0.0.1:9000/api/login",
      out: 'HTTP/1.1 204 No Content\nServer: BaseHTTP/0.6 Python/3.14.10\nDate: Wed, 25 Nov 2026 09:43:59 GMT\nAccess-Control-Allow-Origin: http://127.0.0.1:8088\nVary: Origin\nAccess-Control-Allow-Headers: Authorization, Content-Type\nAccess-Control-Allow-Methods: GET, POST, OPTIONS',
      note: '注意按 RFC 9110 §8.6，204 No Content 响应不得携带 Content-Length。浏览器核对来源、方法与请求头均获准后才会发真正的 POST；而 curl 不执行同源策略，所以 CORS 永远不是防 curl 调接口的服务端防火墙。',
    },
  ]}
/>

对比看本站的 Nginx 架构：当浏览器访问 `http://127.0.0.1:8088/` 并请求同域同端口的 `http://127.0.0.1:8088/api/login` 时，前端与接口属于**同源（Same-Origin）**，通常完全不会触发跨源 CORS 预检。

### 2. 登录拿到 JWT，再亲手把它拆开

**JWT（JSON Web Token，[RFC 7519](#source-rfc7519)）** 最常见的是**三段 JWS 紧凑形态**（规范里也存在加密形态 JWE，这里聚焦最常见的签名/MAC 形态），由三段 Base64URL 字符串用英文句点 `.` 拼成：`Header.Payload.Signature`。

    },
    {

## 三、认证 ≠ 授权与真实上线配置边界

### 1. 用同一个真 Token 测出「认证」和「授权」的分界线

实战和 SRC 里占比极高的一类问题叫**失效访问控制 / 对象级越权（IDOR / BOLA）**（来源：[OWASP A01:2021](#source-owasp-a01-bac)）。很多新手写完后端登录校验，就以为接口已经安全了——其实验完 Token 只回答了**「你是谁（认证，Authentication）」**，还没回答**「你能不能看这条数据（授权，Authorization）」**。

先看未带令牌访问受保护接口 `/api/profile`（返回 `401` 且按 [RFC 9110](#source-rfc9110) 附带 `WWW-Authenticate: Bearer` 质询头），再用 Alice（`uid=101`）的真 Token 分别请求自己和 Bob（`uid=102`）的资料：

<TerminalSession
  environment="KALI 终端 B"
  title="对比：未认证 401 vs 已认证读自己 200 vs 越权读他人 403"
  steps={[
    {
      cmd: "curl --noproxy '*' -sS -i 'http://127.0.0.1:8088/api/profile'",
      out: 'HTTP/1.1 401 Unauthorized\nServer: nginx/1.30.4\n…\nWWW-Authenticate: Bearer realm="modern-web-lab"\n\n{\n  "error": "missing Bearer token"\n}',
      note: '缺少或无效凭据属于未通过认证，返回 401 并通过 WWW-Authenticate 告知客户端认证方式为 Bearer。',
    },
    {
      cmd: `curl --noproxy '*' -sS -i -H "Authorization: Bearer $TOKEN" 'http://127.0.0.1:8088/api/profile?uid=101'`,
      out: 'HTTP/1.1 200 OK\nServer: nginx/1.30.4\n…\n{\n  "uid": 101,\n  "username": "alice",\n  "role": "student",\n  "note": "Alice 的个人实验记录"\n}',
      note: 'Token 里的 uid 与请求的 uid 都是 101，认证和授权同时通过。',
    },
    {
      cmd: `curl --noproxy '*' -sS -i -H "Authorization: Bearer $TOKEN" 'http://127.0.0.1:8088/api/profile?uid=102'`,
      out: 'HTTP/1.1 403 Forbidden\nServer: nginx/1.30.4\n…\n{\n  "error": "forbidden",\n  "detail": "authenticated as alice (uid=101), cannot read uid=102"\n}',
      note: '本示例按常见 HTTP 语义返回 403：服务端认出了你是 Alice，但拒绝你读取他人记录（部分线上系统为避免暴露对象 ID 是否存在，也会刻意统一返回 404）。如果业务代码漏掉这一行归属比对，改一个数字就能读走全站用户数据。',
    },
  ]}
/>

<KeyTakeaway>
现代 Web 往往由 Nginx 统一接入，把静态前端与 JSON API 拆开：同源经反代时通常无需跨源预检，跨源触发预检时由浏览器按 CORS 规则核对来源、方法与请求头；常见三段 JWS 形态 JWT 的前两段只是 Base64URL 编码而非加密；认证通过（非 401）也绝不等于授权通过（防 403 越权）。下一课我们补齐远程运维的 SSH 密钥隧道与底层 tcpdump 流量抓包。
