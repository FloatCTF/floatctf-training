## 引导问题：单引号为什么能改写查询？

登录接口把用户名和密码拼进：

```sql
SELECT * FROM users WHERE username='...' AND password='...'
```

若用户名是 `admin' OR '1'='1' --`，引号会提前结束字符串字面量，后续片段被数据库当作 SQL 语法解析。查询不再只是“匹配这一对凭据”，而是变成攻击者重写后的谓词。

CWE-89 将这类问题描述为未正确中和 SQL 命令中的特殊元素；OWASP 强调应把不可信数据与语句结构分离。（来源：[CWE-89](#source-cwe-89)、[OWASP](#source-owasp-sqli-prevention)）

## 机制：从字符串到执行计划

1. **输入进入查询构造。** 搜索、排序、筛选、登录都可能拼接 SQL。
2. **词法与语法分析。** 数据库把文本切成 token，并生成抽象语法树（AST）。
3. **语义被固定。** 一旦 AST 形成，优化与执行都按这棵树进行。
4. **注入改写 AST。** 闭合引号、追加 `OR`、注释后续条件，都能改变树结构。
5. **影响取决于权限。** 数据库账号能读什么、写什么、调用什么过程，决定上限。

成立条件可以写成：**应用用字符串构造 SQL + 输入影响该字符串 + 缺少结构绑定或等价安全 API**。

<Callout variant="warning" title="过滤单引号不是主防线">
不同数据库、编码转换、数值上下文和二次拼接都会让字符黑名单失效。优先固定语句结构，再处理业务允许的标识符白名单。
</Callout>

## 常见错误与边界

- **把“转义”当成完成修复。** 主防线是结构绑定。
- **忽略动态标识符。** `ORDER BY`、表名通常不能参数化，需要白名单。
- **只测登录框。** 搜索、导出、后台筛选同样常见。
- **数据库账号权限过大。** 注入影响随权限扩大。
- **错误信息过详。** 详细报错会把探测成本降到接近零。

<KeyTakeaway>
SQL 注入的核心是“数据被当成语法”。把语句结构固定下来，让输入只能当值；再对动态标识符、权限、错误回显和二次拼接做独立控制。
