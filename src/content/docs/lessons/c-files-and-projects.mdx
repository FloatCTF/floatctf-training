## 引导问题：程序长大以后

第 10 课你用 Python 统计过日志里的 404。同一件事用 C 写，需要自己打开文件、自己准备存放每一行的缓冲区、自己检查每一步有没有失败。

再往后，程序会变长。所有代码挤在一个文件里，改一个字就要全部重新编译；几个人合作时，大家还会不停地在同一个文件上冲突。

所以真实的 C 工程是这样的：代码分散在很多文件里，各自编译，最后链接；再用一个工具记住它们之间的关系。下学期读开源软件的源码时，第一眼看到的就是这种结构。

### 1. 三个文件

下面这个小工程有三个文件。`stats.c` 里是两个做统计的函数，`main.c` 调用它们：

<CodeFile file="labs/c-files-and-projects/stats.h" note="头文件：两个函数的原型。" />

<CodeFile file="labs/c-files-and-projects/stats.c" mark="1" note="函数的定义。" />

<CodeFile file="labs/c-files-and-projects/main.c" mark="2" note="使用这两个函数的地方。" />

第 21 课讲过：调用一个函数之前，编译器必须先见过它的原型。`main.c` 要调用 `total` 和 `largest`，而它们定义在另一个文件里。办法是把原型写进一个**头文件** `stats.h`，谁要用就 `#include` 它。

<DataTable
  caption="各放什么"
  headers={["文件", "放什么", "谁包含它"]}
  rows={[
    ["stats.h", "函数的原型，结构体的定义。只有声明，没有函数体", "main.c 和 stats.c 都包含"],
    ["stats.c", "函数的定义", "不被包含。它单独编译"],
    ["main.c", "main，以及对那些函数的调用", "不被包含"],
  ]}
  columnRatios={[0.7, 2.6, 1.6]}
/>

两处细节：

- `#include "stats.h"` 用的是双引号，表示在当前目录里找这个文件。尖括号 `<stdio.h>` 是到系统目录里找。
- `stats.h` 开头的 `#ifndef STATS_H`、`#define STATS_H` 和结尾的 `#endif` 是固定写法，防止同一个头文件被重复包含。每个头文件都照这样包一层，名字换成自己的。

（来源：[Beej's Guide: Multifile Projects](#source-beej-multifile)）

### 2. 分开编译，再链接

<TerminalSession
  title="每个 .c 各自编译成 .o"
  steps={[
    { cmd: 'gcc -Wall -c main.c', note: '第 19 课学的 -c：只编译，不链接，得到 main.o。' },
    { cmd: 'gcc -Wall -c stats.c' },
    { cmd: 'gcc main.o stats.o -o report', note: '把两个目标文件链接成可执行文件。' },
    { cmd: './report', out: 'total   7808\nlargest 4096' },

/>

分开编译的好处：改了 `stats.c`，只需要重新编译它，再重新链接；`main.c` 不用动。文件越多，省下的时间越可观。

## 三、Makefile：只重做变过的部分

### 1. 把依赖关系写下来

每次都手敲三条命令，文件一多就记不住了，更记不住改了某个文件之后哪些需要重新编译。**make** 是专门做这件事的工具。它读一个名叫 `Makefile` 的文件：

<CodeFile file="labs/c-files-and-projects/Makefile" lang="makefile" note="保存为 ~/lab/c/Makefile，没有扩展名。命令那几行的开头必须是一个 Tab，不能是空格。" />

`Makefile` 由一条条**规则**组成，每条规则是这个样子：

```text
目标: 依赖 依赖 …
<Tab>命令
```

<DataTable
  caption="读第一条规则"
  headers={["部分", "这里的内容", "含义"]}
  rows={[
    ["目标", "report", "要生成的文件"],
    ["依赖", "main.o stats.o", "生成它需要哪些文件。它们当中任何一个比目标新，目标就过时了"],
    ["命令", "gcc main.o stats.o -o report", "怎样生成"],
  ]}
  columnRatios={[0.6, 1.6, 2.8]}

（来源：[GNU make: What a Rule Looks Like](#source-make-rules)）

### 2. 让 make 干活

<TerminalSession
  title="同一条命令，四种反应"
  steps={[
    { cmd: 'rm -f report main.o stats.o', note: '先把刚才手工编译的产物删掉，从头来。' },
    { cmd: 'make', out: 'gcc -Wall -c main.c\ngcc -Wall -c stats.c\ngcc main.o stats.o -o report', note: 'make 把它执行的每条命令都打印出来。它从第一条规则开始：要 report，先得有 main.o 和 stats.o，于是先去做它们。' },
    { cmd: './report', out: 'total   7808\nlargest 4096' },
    { cmd: 'make', out: "make: 'report' is up to date.", note: '什么都没变，什么都不用做。' },
    { cmd: 'touch stats.c', note: 'touch 把文件的修改时间更新为现在，相当于假装改了它。' },
    { cmd: 'make', out: 'gcc -Wall -c stats.c\ngcc main.o stats.o -o report', note: '只重新编译了 stats.c，然后重新链接。main.c 没有动。' },
    { cmd: 'make clean', out: 'rm -f report main.o stats.o', note: 'make 后面可以写目标的名字。clean 这条规则没有依赖，命令是删掉所有产物。' },
  ]}
/>

make 的判断方法很朴素：**比较修改时间。** 目标不存在，或者有任何一个依赖比目标新，就执行那条规则的命令。（来源：[GNU make: How make Processes a Makefile](#source-make-how)、[make(1)](#source-man-make)）

所以依赖要写全。`main.o` 那一行写着 `main.c stats.h`：`main.c` 包含了 `stats.h`，头文件改了，`main.c` 也得重新编译。漏写了 `stats.h`，改完头文件再 `make`，它会告诉你一切都是最新的，而你运行的是旧程序。

局限：这里的 Makefile 是最小的写法，每个文件一条规则。真实工程会用变量和通配规则来避免重复，大型工程往往用 CMake 这类工具自动生成 Makefile。它们的核心都是今天这三样：目标、依赖、命令。

<KeyTakeaway>
读写文件靠 `FILE *`：`fopen` 打开，`fgets` 逐行读，`fprintf` 写，`fclose` 关；`fopen` 失败返回 `NULL`，必须检查。程序拆成多个文件时，头文件放原型给大家包含，每个源文件单独编译成目标文件，最后链接到一起。Makefile 把「谁依赖谁、怎样生成」写下来，make 靠比较文件的修改时间，只重做过时的部分。
</KeyTakeaway>
