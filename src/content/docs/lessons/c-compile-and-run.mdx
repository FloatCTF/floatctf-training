## 引导问题：Kali 里的命令是什么做的

第 2 课你用 `ls`，第 3 课用 `grep`、`sort`，第 13 课用 `curl`。它们不是 Python 脚本。用 `file` 看一眼：

```text
/usr/bin/ls: ELF 64-bit LSB pie executable, x86-64, …
```

`ls` 是一个里面全是机器指令的二进制文件。它当初是用 C 写的，然后被**编译**成了这个样子。操作系统本身、Python 解释器、你用的大多数命令，都是这么来的。

下学期要分析的程序，绝大多数也是这种文件。想读懂它们为什么会出问题，得先自己写过、编译过。

## 二、把四步拆开看

`gcc hello.c -o hello` 这一条命令，里面其实做了四件事：

<FlowSimulator client:visible title="从源码到可执行文件的四步" steps={pipeline} motionLevel="explanatory" />

（来源：[gcc(1)](#source-man-gcc)）

`gcc` 有三个选项，可以让它做到某一步就停下。下面一步一步来。

### 1. 预处理：-E

<TerminalSession
  title="只做预处理"
  steps={[
    { cmd: 'gcc -E hello.c | wc -l', out: '844', note: '-E 把预处理的结果打印出来。六行的源文件变成了八百多行。' },
    { cmd: 'gcc -E hello.c | tail -n 6', out: '\n# 3 "hello.c"\nint main(void) {\n    printf("Hello, C!\\n");\n    return 0;\n}', note: '看最后六行：你写的 main 原封不动地在最后。前面那八百多行是 stdio.h 的内容，#include 那一行被它们替换掉了。' },
  ]}
/>

以 `#` 开头的行不是 C 语句，是写给**预处理器**的指令。`#include <stdio.h>` 的意思就是「把这个文件的内容粘贴到这里」。（来源：[Beej's Guide: Hello, World!](#source-beej-hello)）

### 2. 编译：-S

<TerminalSession
  title="翻译成汇编"
  steps={[
    { cmd: 'gcc -S hello.c', note: '-S 做到编译这一步为止，生成 hello.s。' },
    { cmd: 'wc -l hello.s', out: '28 hello.s' },
    { cmd: "grep -n 'main:\\|call\\|ret' hello.s", out: '9:main:\n19:\tcall\tputs@PLT\n23:\tret', note: '挑三行看：main 从第 9 行开始，第 19 行调用了一个函数，第 23 行返回。' },
  ]}
/>

`hello.s` 是**汇编代码**：每一行对应处理器的一条指令，仍然是给人看的文本。现在不需要读懂它，下学期的逆向课会从这里开始。

有一处值得留意：你写的是 `printf`，汇编里调用的却是 `puts`。编译器发现这次只是打印一个固定的字符串，就换成了更简单的函数。**编译器生成的代码不一定和你写的一一对应。**

### 3. 汇编：-c

<TerminalSession
  title="翻译成机器码"
  steps={[
    { cmd: 'gcc -c hello.c', note: '-c 做到汇编这一步为止，生成 hello.o，叫目标文件。' },
    { cmd: 'file hello.o', out: 'hello.o: ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV), not stripped', note: 'relocatable：里面已经是机器码，但还没有定下来放在内存的什么位置，也还缺 puts 的代码。' },
  ]}
/>

### 4. 链接

<TerminalSession
  title="把目标文件接成可执行文件"
  steps={[
    { cmd: 'gcc hello.o -o hello', note: '给 gcc 的是 .o 文件，它就只做最后一步：链接。' },
    { cmd: 'file hello', out: 'hello: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2, BuildID[sha1]=7bbf8521f9dffa5d6bfbd12c71bf2d15ace5e88c, for GNU/Linux 3.2.0, not stripped', note: 'executable：可以运行了。和引导问题里 ls 的类型一样。BuildID 那一串与你的可能不同。' },
    { cmd: './hello', out: 'Hello, C!' },
  ]}
/>

你的程序调用了 `puts`，但你没有写过它。它的机器码在系统的 C 库里。**链接**做的就是把你的目标文件和用到的库接在一起，让每一处函数调用都找得到对应的代码。

<DataTable
  caption="四步的产物"
  headers={["步骤", "选项", "输入", "输出", "是文本还是二进制"]}
  rows={[
    ["预处理", "-E", "hello.c", "展开之后的 C 源码", "文本"],
    ["编译", "-S", "预处理的结果", "hello.s，汇编代码", "文本"],
    ["汇编", "-c", "汇编代码", "hello.o，目标文件", "二进制"],
    ["链接", "不加选项", "hello.o 和 C 库", "hello，可执行文件", "二进制"],
  ]}
  columnRatios={[0.7, 0.8, 1.3, 1.6, 1.1]}
/>

（来源：[gcc(1)](#source-man-gcc)、[file(1)](#source-man-file)）

平时不需要分四步做，一条 `gcc hello.c -o hello` 就够。把它拆开，是为了报错时知道问题出在哪一步。

## 三、退出状态与读报错

### 1. main 的返回值去哪了

<CodeFile file="labs/c-compile-and-run/status.c" note="保存为 ~/lab/c/status.c。" />

<TerminalSession
  title="程序结束时留下的一个数"
  steps={[
    { cmd: 'gcc status.c -o status' },
    { cmd: './status', out: 'about to return 42' },
    { cmd: 'echo $?', out: '42', note: '$? 是 shell 里的一个特殊变量：上一条命令的退出状态。它就是 main 返回的那个数。' },
    { cmd: './hello', out: 'Hello, C!' },
    { cmd: 'echo $?', out: '0' },
  ]}
/>

每个程序结束时都会交给系统一个整数，叫**退出状态**。约定是 0 表示成功，非 0 表示出了某种问题。shell 脚本和其他程序靠它判断一条命令成没成功。（来源：[N1570](#source-n1570)、[Zsh: Shell Grammar](#source-zsh-grammar)）

### 3. 链接阶段的报错

<CodeFile file="labs/c-compile-and-run/bad_link.c" mark="3" note="第 3 行只是声明「有一个叫 greet 的函数」，但哪里都没有写出它的函数体。" />

<TerminalSession
  title="声明了，却没有定义"
  steps={[
    {
      cmd: 'gcc bad_link.c -o bad',
      out: "/usr/bin/x86_64-linux-gnu-ld.bfd: /tmp/ccJFCeuy.o: in function `main':\nbad_link.c:(.text+0x5): undefined reference to `greet'\ncollect2: error: ld returned 1 exit status",
      note: '这次的样子不同：没有行号和箭头，报错的是 ld，也就是链接器。/tmp/cc… 是临时文件，名字每次不同。',
    },
  ]}
/>

编译这一步通过了，因为第 3 行向编译器保证了「greet 存在」。到链接时要找它的机器码，找不到，于是报 `undefined reference`。

### 4. 警告和 -Wall

<CodeFile file="labs/c-compile-and-run/warn.c" mark="4" note="第 4 行的变量定义了却从来没用过。" />

<TerminalSession
  title="能编译，但有可疑之处"
  steps={[
    { cmd: 'gcc warn.c -o warn', note: '默认情况下什么都不说。' },
    {
      cmd: 'gcc -Wall warn.c -o warn',
      out: 'warn.c: In function ‘main’:\nwarn.c:4:9: warning: unused variable ‘unused’ [-Wunused-variable]\n    4 |     int unused = 5;\n      |         ^~~~~~',
      note: '-Wall 打开一批常用的警告。warning 不阻止编译，可执行文件照样生成。',
    },
    { cmd: './warn', out: 'done' },
  ]}
/>

`error` 是编译器无法继续，`warning` 是编译器能继续但觉得你可能写错了。在 C 里，很多真正的错误只会以 warning 的形式出现，之后几课会见到。**从现在起，编译时一律加上 `-Wall`，并把每一条 warning 当作 error 来对待。**

<KeyTakeaway>
C 程序要先编译再运行。`gcc` 依次做预处理、编译、汇编、链接四步，把文本形式的源码变成二进制的可执行文件；运行的是这个文件，源码改了必须重新编译。程序从 `main` 开始，它的返回值是程序的退出状态，用 `echo $?` 查看。报错带行号和列号的来自编译器，写着 `undefined reference` 和 `ld` 的来自链接器。编译时始终加 `-Wall`。
</KeyTakeaway>
