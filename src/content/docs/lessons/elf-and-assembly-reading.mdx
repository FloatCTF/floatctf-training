## 引导问题：编译出来的二进制像一团乱码，分析的人到底在看什么

第 19 课你已经知道 `gcc` 把 `.c` 源码译成了机器码，用编辑器直接打开全是乱码。假如别人发来一个叫 `check_pin` 的校验程序，不给源码，怎么知道它究竟在比对哪个数字？

靠的不是硬猜，而是按顺序把 ELF 文件的结构和关键函数的机器码反译出来读。先拖动五步条，看清一个 ELF 文件从磁盘走到 CPU 的过程：

## 三、用 `objdump` 逐行读懂真实反汇编

加上 `-M intel` 让 `objdump` 按目标在左、源在右的 Intel 语法输出（来源：[objdump 文档](#source-binutils-objdump)）。先用下面的交互步进器单步跟着 `rip` 走一遍 `check_pin`，再和终端里的原始反汇编逐行对照：

<Callout variant="info" title="什么时候用 objdump，什么时候上反编译器">
几十行的小函数直接看 `objdump -d -M intel` 最直接，输出即文件内的原始机器指令反汇编（注意静态反汇编只展示潜在代码路径，不能单独证明某条路径在运行时一定被执行）。遇到几万行的大程序或去符号（stripped）二进制时，再配合 Ghidra、IDA 或 Binary Ninja 辅助阅读，并用这里的基础汇编核对伪代码细节。
</Callout>

<KeyTakeaway>
分析 Linux 二进制按固定顺序推进：file 确认架构与链接方式，readelf 查看 ELF 头与节区，strings 提取静态字符串，再用 objdump -d -M intel 对照 rdi/rsi/rax 与 cmp/jne 把汇编和 C 逻辑对应起来。
</KeyTakeaway>
