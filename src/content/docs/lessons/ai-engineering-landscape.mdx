## 二、能力接入层：Function Calling 与无状态 MCP

### 1. Function Calling：模型出主意，代码真干活

大模型本身碰不到数据库，也发不了 HTTP 请求。**Function Calling** 的契约非常干净（来源：[OpenAI Function Calling](#source-openai-function-calling)）：开发者先用 JSON Schema 声明自己有哪些函数、参数长什么样；用户问「订单 SO-2049 到哪了」，模型只返回一段结构化调用请求：

```json
{
  "type": "function_call",
  "call_id": "call_8f2a",
  "name": "get_order_status",
  "arguments": "{\"order_id\":\"SO-2049\"}"
}
```

真正去查库的是你的业务代码，查完再把结果塞回上下文让模型整理回答。记住这个分权原则：**模型只负责「提议调什么、传什么参」，执行权、鉴权和审计永远握在应用代码手里。**

三个常混的词一句话理顺：**Tool Use** 指「模型用工具」这件事本身；**Function Calling** 是具体某家模型 API 的调用格式；**MCP** 则是跨应用、跨厂商的统一协议。

### 2. Stateless MCP：为什么新规范把会话拿掉了

早期远程 MCP 服务如果把客户端会话（`Mcp-Session-Id`）只保存在单台服务器内存里，部署就会受限：负载均衡需要配粘性路由，机器重启会话就断。2025 年引入 Streamable HTTP，2026 年 7 月的规范修订进一步移除协议级会话，让 **无状态（Stateless）MCP** 成为默认形态（来源：[MCP Streamable HTTP transport](#source-mcp-streamable-http)）：

```text
有状态部署：客户端绑死在一台机器上 → 扩缩容麻烦、重启断连
无状态部署：每个请求自带所需信息 → 像普通 HTTP API 一样随便加机器、随便轮询
```

确实要跨请求存状态时，把状态外置到 Redis/数据库或带在请求参数里，服务实例本身保持轻盈无状态。

## 三、知识与记忆层：RAG、向量检索与分层记忆

### 1. RAG：与其硬背新知识，不如给模型带本开卷参考书

模型训完那一刻，权重里的知识就定格了。公司昨天刚改的退款政策、内部接口文档，它压根不知道。**RAG（检索增强生成）**的解法很朴素（来源：[RAG 原论文](#source-rag-paper)）：把知识放在外面的索引库里，用户来问时，先检索出最相关的几段原文塞进提示词，再让模型照着原文作答。政策变了，换一下外部索引就行，不用重训模型。

「RAG 2.0」最早是 Contextual AI 在 2024 年提出的厂商说法，指把检索器和语言模型联合端到端训练，而不是拿冻结组件硬拼（来源：[Introducing RAG 2.0](#source-rag2-contextual)）。社区平时也常拿它泛指加了混合检索、重排、多跳查询的进阶 RAG——聊天听到这个词，先对齐对方指哪一种。
</Callout>

### 2. 向量数据库与 HNSW：大规模语义检索怎么提速

## 四、模型定制层：什么时候才真的该动权重

### 1. 先排查，再选招：Prompt → RAG → 微调

新手一上来最爱问「我们要不要微调一个自己的大模型？」。OpenAI 官方优化指南给了一张非常冷静的决策表（来源：[Optimizing LLM Accuracy](#source-openai-accuracy-guide)、[Supervised fine-tuning](#source-openai-sft-guide)）：

<DataTable
  caption="按失败原因挑优化手段，别一上来就硬上微调"
  headers={["出什么毛病", "典型表现", "优先用哪招", "背后的道理"]}
  rows={[
    ["没说清楚规矩", "格式跑偏、理解错意图", "改 Prompt", "成本最低，几分钟验证完"],
    ["缺新知识 / 业务资料", "瞎编公司政策、信息过期", "上 RAG", "事实会变，放索引里秒级更新；写进权重难维护"],
    ["风格或复杂格式不稳", "怎么叮嘱都偶发错格式、口吻不对", "微调（SFT）", "拿几百几千条示范把固定习惯压进权重"],
    ["既缺知识又不稳", "垂直领域专业术语 + 严苛格式", "微调 + RAG", "微调管习惯与格式，RAG 管实时事实"],
  ]}
/>

记住一句话：**微调擅长教模型「怎么说话、按什么格式干活」，不擅长往脑子里硬塞天天变动的事实——那是 RAG 的活。** 而且动手微调之前，必须先有评测集，否则训完根本不知道是变好了还是训傻了。

### 2. LoRA 与蒸馏：花小钱办大事的两项定制手艺

- **LoRA（低秩适配）**：把几百亿参数的原模型权重 `W` 原封不动冻住，只在旁边挂两个很瘦的小矩阵 `B` 和 `A` 去学增量 `ΔW = B × A`。在 GPT-3 175B 上，LoRA 把需要训练的参数量压低了约一万倍，产出的适配器文件小巧易切换；上线时还能直接把 `BA` 加回 `W`，推理零额外延迟（来源：[LoRA 原论文](#source-lora-paper)）。

<LoraDecomposition />

- **知识蒸馏（Distillation）**：拿又大又贵的「教师模型」在特定任务上的输出（尤其是带相对概率分布的软标签）去教一个小巧便宜的「学生模型」（来源：[Hinton 知识蒸馏原论文](#source-distillation-paper)）。在生产里，蒸馏常用来在收窄的垂直任务上逼近大模型质量，同时显著压低单次推理的延迟与成本（实际收益需在目标任务集上对照质量与单次推理开销实测）。

<DistillationComparison />

### 3. 合成数据：既能造出好模型，也能引发「模型坍缩」

高质量人工标注又贵又慢，现在很多强模型大量使用**合成数据**——比如微软的 **Phi-4** 技术报告披露，其预训练数据里有 40% 合成数据加上 15% 网页改写（归属合成子类，合计超半数），通过多智能体出题和自我修订提纯质量（来源：[Phi-4 Technical Report](#source-phi4-report)）。

但合成数据不是无脑无限循环印钞机。Nature 2024 论文研究过「不加筛选、一代接一代拿上一个模型的输出去训下一代」的极端情况：随着代数增加，模型会先丢掉长尾小众样本，分布逐步退化失真，称为**模型坍缩（Model Collapse）**（来源：[Nature 2024 模型坍缩论文](#source-model-collapse-nature)）。这提醒工程团队：合成数据必须做好来源标记、质量过滤和真实人类数据配比校验，别让模型关起门来吃自己的回锅肉。

## 五、质量与安全层：发版前跑评测，运行时架护栏

### 1. 评测框架与 LLM-as-a-judge

没有回归测试，改 AI 系统就像蒙眼走钢丝。一套评测框架包含三件：**代表真实线上场景的数据集、自动打分器（代码规则或模型裁判）、阻断退化的 CI 门禁**（来源：[Demystifying evals for AI agents](#source-anthropic-agent-evals)）。

对于写摘要、客服回复这种没法写死正则表达式的开放题，业界常用 **LLM-as-a-judge**（让更强的模型按打分细则当裁判）。MT-Bench 与 Chatbot Arena 论文实测，GPT-4 裁判和人类偏好的一致率超过 80%，跟人类互相之间的一致率差不多——但它自带三大毛病：**偏向排前面的选项（位置偏差）、偏爱写得长的话（冗长偏差）、偏爱自己生成的答案（自我增强偏差）**（来源：[Judging LLM-as-a-Judge](#source-llm-judge-paper)）。

<Callout variant="warning" title="裁判自己也得先过考试">
用模型当自动裁判时，务必做「交换选项顺序重评」来抵消位置偏差，并先在人工抽检集上核对裁判和人类打分的一致率，再放心放进 CI。
</Callout>

### 2. Guardrails（运行时护栏）

评测管发版前，**Guardrails** 管线上每一条真实请求。比如 NVIDIA NeMo Guardrails 把护栏拆成输入、检索、对话、执行、输出五道轨道，在各个卡口检查越界话题、敏感泄露和非法调用（来源：[NeMo Guardrails Overview](#source-nemo-guardrails-docs)）。

护栏面对的头号对手就是 OWASP LLM 2025 排名第一的**提示注入（LLM01）**，OWASP 明确提醒：RAG 和微调都防不住注入（来源：[OWASP Top 10 for LLMs 2025](#source-owasp-llm-top10)）。护栏怎么攻、怎么破、又怎么叠多层防线，下一课《AI 安全》专门掰开讲。

## 六、运行与成本层：看得见、管得住、算清账

### 1. 可观测性：一次请求慢在哪、花了多少 token

一个线上 Agent 请求可能连调三次模型、两次工具、一次检索。一旦用户投诉「卡了 7 秒」或账单暴涨，必须靠分布式 **Trace** 把每一步拆成耗时和 token 明细（OpenTelemetry 正在推进 `gen_ai` 语义约定来统一字段名，目前仍处于 Development 演进阶段，老版本升级时注意兼容迁移说明，来源：[OTel GenAI 约定](#source-otel-genai-spec)、[OTel GenAI 仓库](#source-otel-genai-repo)、[OTel v1.37.0 说明](#source-otel-genai-v137)）：

```text
示意 Trace：客服请求 #8f2a（各段耗时合计 5.24s，模型 token 合计 21,230）
├── gateway.route          120ms
├── guardrails.input        80ms
├── retrieval.search       340ms   top-k=8
├── gen_ai.chat  (第 1 轮)  2.1s    input 18,200 / output 240
├── tool.get_order_status  610ms
├── gen_ai.chat  (第 2 轮)  1.9s    input 2,300 / output 490
└── guardrails.output       90ms
```

一眼就能抓出重点：第 1 轮输入高达 18,200 token，接下来就该去查哪些是重复的系统提示和工具定义，能不能吃上提示缓存。

### 2. AI 网关与成本账本：提示缓存到底省多少

业务同时接两三家模型供应商时，鉴权、限流、日志、失败自动切备用模型、以及「简单问题走小模型、难题走旗舰模型」的路由策略，全收进统一的 **AI 网关**（如 Cloudflare AI Gateway，来源：[Cloudflare AI Gateway](#source-cloudflare-ai-gateway)）。

最后算一笔最立竿见影的省钱账——**提示缓存（Prompt Caching）**。以 Anthropic 官方 5 分钟缓存倍率为例：第一次写入按基础输入价的 **1.25 倍**收费，之后每次命中读取只要 **0.1 倍**（来源：[Anthropic Prompt Caching](#source-anthropic-prompt-caching)）。

**在满足缓存条件下，从第 2 次命中起就已经回本了！** 不过实际省钱需要同时满足三个前提：一是前缀长度达到对应模型的**最低可缓存门槛**（例如部分旗舰或轻量模型要求至少 4,096 token，低于门槛不会触发写入），二是缓存边界内的前缀必须逐字完全一致（千万别把每次都会变的「当前精确时间戳」插在系统提示最开头），三是后续请求落在缓存有效期内持续命中。

## 常见误区与工程边界

- **别用微调硬塞动态事实**：政策、库存、文档会天天变，老老实实放 RAG 检索层，微调留给固化格式和口吻。
- **向量搜索不是百分百精确**：HNSW 是近似最近邻，关键业务要测召回率，必要时用「关键词 + 向量」混合检索加结构化权限过滤。
- **别把动态时间塞进缓存前缀**：哪怕前缀开头差一个字符，整个提示缓存都会穿透重算。
- **护栏挡不住所有注入，评测也不能一劳永逸**：安全防线必须多层叠加，线上失败病例要持续回流进评测集。

下一课《AI 安全：从提示注入到对抗样本》把六层里的「安全」放大十倍，拆开提示注入、真实翻车事件、对抗样本、数据投毒、成员推断和模型提取，收束成一套可以直接用来做安全和打 CTF 的分析框架。
