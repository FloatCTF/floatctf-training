## 引导问题：HTTPS 都加密了，为什么调试代理还能看见明文

第 14 课的明文 HTTP 请求在网络上像明信片一样可读；换成 `https://` 后，中间链路看到的变成密文。可只要你打开 Burp Suite 或 mitmproxy 调网页，浏览器明明走着 HTTPS，代理里却照样一行行显示着请求头、JSON 正文和 Cookie。

并不是 HTTPS 失效了，而是「TLS 到底在哪一端终结」决定了谁能读到明文。要把这条链拆明白，先分清日常常被混叫成「加密」的四类操作，再亲手签一张本地证书、起一台本地代理对照观察。

## 二、HTTPS 与证书链：亲手搭一个本地 CA

**HTTPS** 就是把 HTTP 放进 **TLS**（Transport Layer Security）加密连接里跑。按 [RFC 8446](#source-rfc8446)，TLS 1.3 在通信双方之间建起一条加密、防篡改且经过身份校验的通道。

只加密其实不够——如果半路有人冒充目标服务器和你交换密钥，你们俩聊得再加密，明文也全落进对方手里。为了确认「对面真的是 `127.0.0.1` 或 `example.com`」，互联网用 **PKI 证书链和 CA（证书颁发机构）** 来做身份担保（来源：[RFC 5280](#source-rfc5280)、[RFC 9525](#source-rfc9525)）：

1. 操作系统和浏览器出厂时内置一批受信任的**根 CA 证书**，里面存着根 CA 的公钥。
2. 真实互联网通常走**三级链**：根 CA 给**中间 CA** 签发证书，再由中间 CA 用私钥给网站签 **X.509 站点证书**，避免根 CA 私钥频繁在线使用。为了方便上手，本课实验省略中间 CA，直接用本地根 CA 给站点签发证书。
3. 客户端连上网站后，沿证书链逐级验签直到受信任的根 CA，再检查有效期，并按 [RFC 9525](#source-rfc9525) 核对证书里的 **SAN（Subject Alternative Name）** 是否包含当前访问的域名或 IP。

### 3. Cookie 的三道保护开关与 HTTPS 的边界

刚才那条 `Set-Cookie` 里带着三个常见安全属性（来源：[RFC 6265](#source-rfc6265)、[MDN Set-Cookie](#source-mdn-set-cookie)）：

<DataTable
  caption="Set-Cookie 三个常见保护属性"
  headers={["属性", "管住谁", "漏写会多出什么风险"]}
  rows={[
    ["Secure", "浏览器发送通道", "只允许在 HTTPS 里携带；漏写时若误走明文 HTTP，会话编号可能被同网段嗅探"],
    ["HttpOnly", "页面里的 JavaScript", "禁止用 document.cookie 读取，配合后续 XSS 防御，降低脚本直接偷走会话 Cookie 的机会"],

也要记清 **HTTPS 管不到的地方**：它只保护客户端和服务器之间的网络链路，防 Wi-Fi 窃听和半路篡改。服务端自己写错代码（SQL 注入、越权、直接信前端价格），或者用户电脑上已经装了受信任的本地代理 CA，HTTPS 都拦不住。

## 三、代理抓包与「前端不可信」

很多新手把输入框设成 `readonly`，或者写段 JS 检查价格不能小于 35，就觉得安全了。其实网页和 JS 全跑在用户自己的电脑上。只要在浏览器和服务器之间插一台本地代理，或者干脆用 `curl` 直接发包，前端代码连执行的机会都没有（来源：[OWASP Input Validation Cheat Sheet](#source-owasp-input-validation)）。

### 3. 回到开篇问题：代理遇到 HTTPS 时到底发生了什么

让 `curl` 走同一个 `mini_proxy.py` 去访问前面的 `https://127.0.0.1:8443/whoami`：

<TerminalSession
  environment="KALI 终端 B"
  title="HTTPS 经过普通代理：代理只看到 CONNECT 隧道"
  steps={[
    {
      cmd: "curl --noproxy '' -sS -x http://127.0.0.1:8888 --cacert ca.crt https://127.0.0.1:8443/whoami",
      out: '{\n  "tls_version": "TLSv1.3",\n  "cipher": "TLS_AES_256_GCM_SHA384",\n  "user_agent": "curl/8.23.0",\n  "cookie": "(none)"\n}',
      note: '请求照样成功。切回代理终端看日志，只多出一行：[PROXY] CONNECT tunnel -> 127.0.0.1:8443 (passthrough tunnel, TLS payload not decrypted)。',
    },
  ]}
/>

这就是 [RFC 9110 §9.3.6](#source-rfc9110) 定义的 `CONNECT` 隧道：普通代理只管把字节搬给 `127.0.0.1:8443`，看不到加密后的 HTTP 请求头和正文。

而 **Burp Suite** 和 **mitmproxy** 之所以能看到 HTTPS 明文，靠的正是第二节同一个机制——只不过在浏览器里，是你**手动把代理生成的 CA 根证书导入了测试浏览器信任库**（前面用 `curl --cacert` 只是单次临时信任）。对比看下面两条链路：

<TlsProxyDiagram />

（来源：[How mitmproxy works](#source-mitmproxy-how)、[PortSwigger CA Docs](#source-portswigger-ca)）

记住一条红线：**永远别在主力电脑上装来路不明的根证书**。哪怕是自己调试用的 Burp / mitmproxy 证书，也只装在练习虚拟机或独立测试浏览器配置里，用完顺手关掉代理。

<KeyTakeaway>
TLS 终止在哪里，明文就在哪里出现：普通 CONNECT 代理只转发密文流，而导入测试 CA 的调试代理把连接拆成两段 TLS。HTTPS 与证书链守住的是传输链路，管不到客户端本身——请求离开浏览器即可被代理或 curl 改写，价格、权限与输入校验必须留在服务端。
</KeyTakeaway>
