## 引导问题：既然开了 HTTPS，调试工具凭什么还能看到你的请求

在第 14 课里，你用明文 HTTP 和本地练习站对话，整份请求就像明信片一样暴露在网络里。到了真实网站，地址栏前面几乎都有一把锁（`https://`），大家常说「HTTPS 是加密的，中间人看不见」。

可真开始做现代 Web 调试或安全学习时，你会立刻撞上一个看似矛盾的现象：打开 Burp Suite 或 mitmproxy 之后，浏览器访问 `https://` 网站，代理界面里照样一行行显示着明文请求头、JSON 正文和 Cookie。

是 HTTPS 失效了吗？不是。弄懂这件事，要先分清几类最容易混淆的数据变换，再亲手搭一套本地证书链和一个最小代理。

## 一、先分清几件总被混为一谈的事

## 二、HTTPS 与证书链：亲手搭一个本地 CA

**HTTPS** 就是「在 HTTP 下面垫了一层 **TLS**（Transport Layer Security）」。按 [RFC 8446](#source-rfc8446)，TLS 1.3 在客户端与服务器之间建立一条加密、防篡改且经过身份认证的通信信道。

这里有一个学校很少讲透的关键点：**光加密不够，还得知道你在跟谁加密**。如果路上有人冒充目标服务器和你交换密钥，你俩之间虽然也在加密说话，但对方拿到了你的全部明文。

为了证明「对方真的是 `127.0.0.1` 或 `example.com`」，互联网采用 **PKI 证书链与 CA（Certificate Authority，证书颁发机构）** 体系（来源：[RFC 5280](#source-rfc5280)、[RFC 9525](#source-rfc9525)）：
1. 操作系统和浏览器出厂时内置了一批受信任的**根 CA 证书**（里面有根 CA 公钥）。
2. 真实互联网通常采用**三级证书链**：根 CA 给**中间 CA** 签发证书，再由中间 CA 用私钥给网站签发 **X.509 站点证书**（避免根 CA 私钥频繁在线使用）。本课为简化实验，省略中间 CA，直接用自建的本地根 CA 给站点签发证书。
3. 客户端连上网站时，沿证书链逐级验签直到受信任的根 CA，检查有效期与用途，并按 [RFC 9525](#source-rfc9525) 核对证书里的 **SAN（Subject Alternative Name）** 是否匹配当前访问的域名或 IP。

### 3. Cookie 的三道安全属性与 HTTPS 的真实边界

刚才那条 `Set-Cookie` 里藏着现代 Web 几乎必考的三个属性（来源：[RFC 6265](#source-rfc6265)、[MDN Set-Cookie](#source-mdn-set-cookie)）：

<DataTable
  caption="Set-Cookie 三个常见保护属性"
  headers={["属性", "约束了谁", "没加会多出什么风险"]}
  rows={[

  columnRatios={[1.2, 1.3, 3.0]}
/>

同样要记清 **HTTPS 的边界**：它保护的是「客户端与服务器之间的网络传输链路」（防 Wi-Fi 窃听、运营商插广告、半路改包）；它**不能**防止服务端代码写错（比如 SQL 注入、越权、直接信前端价格），也**不能**防止用户自己电脑上已经安装的受信任根证书或代理去查看流量。

## 三、代理抓包与「前端不可信」

现在把视角转回真实 Web 开发和安全审计中最常用的手段：**HTTP 代理（Proxy）**。

很多人以为「把输入框设成 `readonly`」或者「用 JavaScript 检查价格不能小于 35」就安全了。其实网页和脚本都运行在**用户自己的电脑里**——只要在浏览器和服务器之间插一个本地代理，或者干脆用 `curl` 直接发包，前端限制连触发的机会都没有（来源：[OWASP Input Validation Cheat Sheet](#source-owasp-input-validation)）。

### 3. 回到开篇问题：代理遇到 HTTPS 时发生了什么

现在让 `curl` 通过同一个 `mini_proxy.py` 访问前面的本地 HTTPS 站点 `https://127.0.0.1:8443/whoami`（同样加 `--noproxy ''` 确保确实穿过 8888 代理）：

<TerminalSession
  environment="KALI 终端 B"
  title="HTTPS 经过普通代理：代理只看到 CONNECT 隧道"
  steps={[
    {
      cmd: "curl --noproxy '' -sS -x http://127.0.0.1:8888 --cacert ca.crt https://127.0.0.1:8443/whoami",
      out: '{\n  "tls_version": "TLSv1.3",\n  "cipher": "TLS_AES_256_GCM_SHA384",\n  "user_agent": "curl/8.23.0",\n  "cookie": "(none)"\n}',
      note: '请求照样成功，但回到代理终端看日志，只会多出一行：[PROXY] CONNECT tunnel -> 127.0.0.1:8443 (passthrough tunnel, TLS payload not decrypted)。',
    },
  ]}
/>

这就是 [RFC 9110 §9.3.6](#source-rfc9110) 规定的 `CONNECT` 隧道：普通透传代理只帮客户端把字节原样转发给 `127.0.0.1:8443`，看不到加密后的 HTTP 请求头与正文。

那 **Burp Suite** 和 **mitmproxy** 这类调试代理凭什么能看到 HTTPS 明文？核心机制与第二节「让客户端信任自建 CA」同源，但在浏览器场景里需要**主动把代理生成的 CA 根证书导入测试浏览器的信任库**（前面我们只是对单次 `curl` 用了 `--cacert ca.crt`，并没有改动浏览器信任库）（来源：[How mitmproxy works](#source-mitmproxy-how)、[PortSwigger CA Docs](#source-portswigger-ca)）。拖动下方步骤条看清整条链：

<FlowSimulator client:visible title="调试代理怎样解开 HTTPS：两段 TLS 与本地 CA" steps={proxyChain} motionLevel="explanatory" />

正因为如此，记住一条铁律：**永远不要在日常主机上安装来路不明的根证书**；哪怕是本地调试用的 Burp / mitmproxy 根证书，也最好只装在练习虚拟机（或单独的测试浏览器配置文件）里，用完及时关闭代理。

<KeyTakeaway>
编码不保密、哈希不可逆、对称加密靠共享密钥、非对称用于密钥协商或加密、数字签名验真伪。HTTPS 靠证书链（根 CA → 中间 CA → 站点证书 + SAN）与 TLS 保护传输链路，但保护不了客户端本身——一旦请求离开浏览器，任何前端限制都可被代理或 curl 改写，所有关键校验和业务计算都必须留在服务端。下一课我们把单机练习站升级成真实的前后端分离、API、JWT 与 Nginx 反向代理架构。
</KeyTakeaway>
