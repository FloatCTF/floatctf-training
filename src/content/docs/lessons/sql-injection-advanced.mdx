## 引导问题：参数化之后，为什么还有注入？

基础课已经说明：参数化让输入成为值。进阶问题是：

1. 代码是否调用了真正的参数绑定 API？
2. 业务是否在标识符位置拼接？
3. 是否存在“先入库、后拼接”的二次路径？

任一条件未满足，都会留下对应的注入风险。

## 预编译实际固定了什么

以参数绑定 API 为模型：

1. 应用先定义语句模板，例如 `WHERE name = ?`。
2. 驱动通过数据库 API 传递模板与参数，数据库将参数按值处理。
3. 参数中的引号、注释和关键字不会进入模板的语法位置。
4. 数据库仍可按统计信息和实现选择或调整执行计划。

OWASP 将预编译语句作为首选防御，并提醒并非所有动态 SQL 片段都能占位。（来源：[OWASP](#source-owasp-sqli-prevention)）

<Callout variant="warning" title="真预编译和模拟预编译">
真预编译把语句模板和参数值分开交给数据库，数据库按值处理参数，参数里的引号不会变成语法。模拟预编译由客户端驱动先转义参数，再拼成一条完整 SQL 发出去。PHP PDO 连接 MySQL 时，`PDO::ATTR_EMULATE_PREPARES` 默认就是这种模拟；设为 `false` 才尽量走数据库自己的预编译，驱动无法预编译的语句仍可能退回模拟。模拟模式在错误的字符集下可以被多字节字符绕过转义，所以「代码里写了 prepare」不等于安全边界已经在数据库一侧。审查时要看驱动文档、这个开关、连接字符集，以及最终发出去的是模板加值，还是一整段 SQL。（来源：[PHP PDO 预定义常量](#source-php-pdo-emulate)、[OWASP](#source-owasp-sqli-prevention)）
</Callout>

## 代码审计清单

- **PHP：** 检查是否关闭模拟预处理、是否用绑定 API、是否把请求参数拼进 `ORDER BY`。
- **Java/MyBatis：** `#{}` 绑定值；`${}` 字符串替换，审计所有 `${}`。
- **Python：** `cursor.execute(sql, params)` 正确；`execute(sql % values)` 或 f-string 拼 SQL 危险；Django `raw()`/`extra()` 需重点看。

## 真实案例

CVE-2023-34362 作为基础案例的进阶复盘，重点检查产品中的查询构造与补丁覆盖面。CVE-2025-1094 影响 PostgreSQL 17.3、16.7、15.11、14.16、13.19 之前的版本：特定 libpq quoting API 的结果被用于构造 `psql` 输入时可能形成 SQL 注入；命令行工具路径还涉及 BIG5 与 EUC_TW 或 MULE_INTERNAL 的编码组合。该案例属于特定客户端工具链条件，不代表参数绑定失效。（来源：[CVE-2023-34362](#source-cve-2023-34362)、[CVE-2025-1094](#source-cve-2025-1094)、[PostgreSQL 公告](#source-postgresql-cve-2025-1094)）

## 常见错误与边界

- **只修了一个 DAO，报表模块仍在拼接。**
- **默认信任 ORM，忽略 raw 查询。**
- **用黑名单过滤 `select/union`，在编码与注释面前失效。**
- **忽略最小权限，注入后果被权限放大。**
