## 引导问题：参数化之后，为什么还有注入？

基础课已经说明：参数化让输入成为值。进阶问题是：

1. 驱动是否真的做了服务端预编译？
2. 业务是否在标识符位置拼接？
3. 是否存在“先入库、后拼接”的二次路径？

只要有一处答案是否定的，注入面就还在。

## 预编译实际固定了什么

以“真预编译”为模型：

1. 发送语句模板，例如 `WHERE name = ?`。
2. 数据库完成词法与语法分析，生成固定 AST。
3. 后续只绑定参数值到叶子节点。
4. 参数中的引号、注释和关键字不再具备语法角色。

OWASP 将预编译语句作为首选防御，并提醒并非所有动态 SQL 片段都能占位。（来源：[OWASP](#source-owasp-sqli-prevention)）

<Callout variant="warning" title="模拟预编译的坑">
部分驱动在某些模式下只在客户端转义后发送完整 SQL。配置审查要确认“参数化 API”最终是否走到结构绑定，而不是字符串拼装。
</Callout>

## 代码审计清单

- **PHP：** 检查是否关闭模拟预处理、是否用绑定 API、是否把请求参数拼进 `ORDER BY`。
- **Java/MyBatis：** `#{}` 绑定值；`${}` 字符串替换，审计所有 `${}`。
- **Python：** `cursor.execute(sql, params)` 正确；`execute(sql % values)` 或 f-string 拼 SQL 危险；Django `raw()`/`extra()` 需重点看。

练习：在授权代码库中搜索 `ORDER BY`、`${`、`+ "SELECT`、`execute(f"`，把命中点分类为“值拼接”或“标识符拼接”。

## 真实案例

CVE-2023-34362 展示注入在业务系统中的大规模影响；CVE-2025-1094 提醒边界可能落在客户端工具链，不只在业务 Controller。（来源：[CVE-2023-34362](#source-cve-2023-34362)、[CVE-2025-1094](#source-cve-2025-1094)）

## 常见错误与边界

- **只修了一个 DAO，报表模块仍在拼接。**
- **把 ORM 当银弹，忽略 raw 查询。**
- **用黑名单过滤 `select/union`，在编码与注释面前失效。**
- **忽略最小权限，注入后果被权限放大。**
