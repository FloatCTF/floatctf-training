## 引导问题：一个带单引号的名字

爱尔兰人常见的姓 O'Brien，中间有一个单引号。第 18 课末尾，你用 Python 查过一个叫 `o'brien` 的用户，程序老老实实地回答「没有这个人」。

如果换一种写法，把名字直接拼进 SQL 字符串里，同样的名字会让程序当场报错。一个普通的名字就能把程序弄坏，说明拼接这种写法本身有问题：**数据混进了代码里。** 这一课用 PHP 把两种写法放在一起对比，看清问题出在哪，以及正确的写法为什么不怕。

<DataTable

占位符有两种写法：问号 `?`，按顺序对应 `execute` 数组里的值；命名占位符 `:name`，按名字对应，参数多的时候更清楚。同一条语句里只能用一种。（来源：[PDO::prepare](#source-php-pdo-prepare)、[PDOStatement::execute](#source-php-pdo-execute)、[PDOStatement::fetch](#source-php-pdo-fetch)）

### 2. 拼接的写法为什么会坏

下面这个文件**故意写错**，用来对照：

<CodeFile file="labs/php-pdo-database/bad_find.php" mark="7" note="第 7 行把名字直接拼进了 SQL 文本。" />

<TerminalSession
  title="同样的输入，拼接的版本"
  steps={[
    { cmd: 'php bad_find.php alice', out: "SQL: SELECT name, role FROM users WHERE name = 'alice'\nalice is admin", note: '普通的名字，看起来一切正常。这正是拼接写法危险的地方：平时测不出问题。' },
    {
      cmd: 'php bad_find.php "o\'brien"',
      out: "SQL: SELECT name, role FROM users WHERE name = 'o'brien'\nPHP Fatal error:  Uncaught PDOException: SQLSTATE[HY000]: General error: 1 near \"brien\": syntax error in /home/kali/lab/php/bad_find.php:9\nStack trace:\n#0 /home/kali/lab/php/bad_find.php(9): PDO->query()\n#1 {main}\n  thrown in /home/kali/lab/php/bad_find.php on line 9",
      note: '看打印出来的 SQL：名字里的单引号和外面的单引号配成了一对，字符串在 o 之后就结束了，剩下的 brien\' 成了数据库读不懂的东西。',
    },
  ]}
/>

第 18 课说过，SQL 里的单引号是字符串的边界。把输入拼进 SQL 文本，输入里的字符就有机会改变语句的结构。这里只是一个名字，结果是语法错误；输入完全由外部决定时，被改变的可能不止于此。下学期的 SQL 注入专题讲的就是这件事。

预处理语句不会出现这个问题，原因在于先后顺序：**SQL 的结构先交给数据库定好，值后交，值永远只是值。** PHP 手册的说法是：预处理语句的参数不需要加引号，驱动会自动处理；只用预处理语句的程序，可以确信不会发生 SQL 注入。（来源：[Prepared statements](#source-php-pdo-prepared)）

<Callout variant="danger" title="规矩">
凡是 SQL 里需要放一个来自外部的值，`$_GET`、`$_POST`、`$_COOKIE`、命令行参数、文件内容，一律写占位符，用 `prepare` 加 `execute` 传进去。不要拼接，也不要自己去「转义一下再拼」。
</Callout>

<KeyTakeaway>
PHP 用 PDO 连接数据库，`query` 执行固定的 SQL，`fetch` 和 `fetchAll` 取出结果。SQL 里只要有来自外部的值，就用 `prepare` 写占位符、用 `execute` 单独把值交过去：语句的结构先定好，值永远只是值。把输入拼进 SQL 文本，输入里的字符就可能改变语句的结构，一个带单引号的名字就足以让它出错。进 SQL 用占位符，进 HTML 用 `htmlspecialchars`，道理相同：数据不能被当成代码。
</KeyTakeaway>
