## 引导问题：靶场目录里的那几个文件

下学期你会拿到这样的目录：里面有程序代码，还有一个 `Dockerfile` 和一个 `compose.yaml`。说明只有一句：进入目录，执行 `docker compose up -d`，然后访问某个端口。

这一条命令做了很多事：把代码做成镜像，起好几个容器，把它们连起来，把端口发布出来，给数据库准备好存储。这节课用一个很小的项目，把这些事一件一件看清楚。

### 5. 为什么是 0.0.0.0

`CMD` 里写的是 `0.0.0.0:8000`，而第 27 课在 Kali 里写的是 `127.0.0.1:8000`。把它改回 127.0.0.1 试一下：在镜像名后面再写一条命令，就会代替 CMD 运行。

<TerminalSession
  title="让 PHP 只监听容器里的 127.0.0.1"
  steps={[
    { cmd: 'docker run -d --name wrong -p 8001:8000 counter php -S 127.0.0.1:8000', out: '7e50eac51604ead78f191ac08082dbfa4aba68cfce0c4aa05dbbea32ed6db9fe' },
    { cmd: 'curl -sS http://127.0.0.1:8001/', out: 'curl: (56) Recv failure: Connection reset by peer', note: '-sS 不显示进度，但出错时照样打印错误。' },
    { cmd: 'docker rm -f wrong', out: 'wrong' },
  ]}
/>

每个容器有自己的一套网络：一块网卡、一个地址、自己的 127.0.0.1。（来源：[Networking overview](#source-dk-networking)）从发布的端口转进来的请求，到达的是容器网卡上的地址，不是它的 127.0.0.1。只监听 127.0.0.1 的程序收不到这些请求。所以**容器里的服务要监听 0.0.0.0**，也就是这个容器的所有地址。

/>

`down` 删掉了两个容器和网络，但默认不删卷，所以计数还在。要连数据一起清掉，用 `docker compose down -v`。（来源：[docker compose down](#source-dk-compose-down)）

<Callout variant="note" title="为什么 app 要等 10 秒">
停止容器时，Docker 先给容器里的主进程发一个「请退出」的信号（SIGTERM），等一段宽限期（默认 10 秒）还没退出，再强制结束它（SIGKILL）。PHP 的内置服务器在容器里不理会第一个信号，所以每次都要等满 10 秒。nginx 会正常退出，所以 web 很快。这不是出错了，等一会就好。
</Callout>

（来源：[docker container stop](#source-dk-stop)）

把 `index.php` 最后一行的输出改一改。下面用 `sed -i 's/旧/新/' 文件名` 在文件里做一次替换，效果和用编辑器打开、修改、保存一样。

    },
    { cmd: 'curl -s http://127.0.0.1:8080/', out: 'visits so far: 6', note: '新代码生效，计数仍然接着数：重建容器不影响卷。' },
    { cmd: 'docker compose down -v', out: "[+] Running 4/4\n ✔ Container compose-web-1  Removed                                        0.2s\n ✔ Container compose-app-1  Removed                                       10.1s\n…（还有 Volume compose_data 和 Network compose_default 两行 Removed，这两行同时进行，先后顺序每次可能不同）", note: '这次卷也删掉了。' },
  ]}
/>

为什么第一次 `up -d` 没变化？容器里运行的是**镜像里的** index.php，是构建时 COPY 进去的那一份。你改的是本机的文件，镜像没变，Compose 看到配置和镜像都和原来一样，就让容器继续运行。加上 `--build`，Compose 先重新构建镜像；镜像变了，它就用新镜像重建 app。（来源：[docker compose up](#source-dk-compose-up)）

构建时为什么只有 COPY 重做？每条指令对应一层，某一层变了，它和它后面的层都要重做，前面的层直接用缓存。这里变的是 index.php，所以从 COPY 开始重做。这也是为什么 Dockerfile 里把很少变的步骤写在前面、经常变的代码放在后面。（来源：[Docker build cache](#source-dk-build-cache)）

Dockerfile 从一个基础镜像开始，用 RUN、WORKDIR、COPY 一层层加上自己的东西，用 CMD 说明容器启动时运行什么；docker build 把它做成镜像，改动只会让那一层和后面的层重做。容器里的服务要监听 0.0.0.0。compose.yaml 把几个服务、它们的端口和卷写在一起，docker compose up -d 一条命令全部启动；同一个项目里的容器在同一个网络里，用服务名互相访问。down 删除容器和网络，卷默认保留；改了代码要加 --build。
</KeyTakeaway>
