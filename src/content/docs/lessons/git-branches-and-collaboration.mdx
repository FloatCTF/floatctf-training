## 引导问题：想试一个改法，又不想弄坏能跑的版本

`toolbox` 里的脚本现在能正常运行。你想给它加一个功能，但没把握，可能要改好几天，中间会有一段时间跑不起来。

如果直接在现有的历史上一路提交下去，这几天里仓库的最新版本都是坏的。假如这时有人找你要一份能用的版本，或者你发现了一个必须马上修的小错误，就很被动。

两个人合作时问题更明显：你和队友同时改同一个项目，各自提交，最后怎样合到一起？两人恰好改了同一行又该听谁的？

Git 对这两个问题的回答是同一个东西：**分支**。

## 一、分支是一个会移动的名字

### 1. 分支和 HEAD

上一课说过，每个提交都记着自己的上一个提交，提交连成一条链。

**分支**（branch）是指向其中某个提交的一个名字。你一直在用的 `main` 就是一条分支。在某条分支上做一次提交，这个名字就自动移到新提交上。新建一条分支，只是多了一个指向当前提交的名字，不复制任何文件，所以几乎不花时间。

仓库里可以同时有很多条分支，Git 用 **HEAD** 记住你现在在哪一条上。上一课 `git log` 输出里的 `(HEAD -> main)` 就是这个意思：你在 `main` 上，`main` 指着这个提交。

**切换分支**做两件事：把 HEAD 移到另一条分支上，再把工作区里的文件换成那条分支所指提交的样子。（来源：[Pro Git: Branches in a Nutshell](#source-progit-branches)、[git-switch](#source-git-switch)）

### 2. 快进合并

<TerminalSession
  title="切回 main，把 feature/banner 合并进来"
  steps={[
    { cmd: 'git switch main', out: "Switched to branch 'main'" },
    { cmd: 'ls', out: 'portcheck.py  README.md  secret.txt', note: 'banner.py 不见了。工作区被换成了 main 所指提交的样子，那个提交里没有它。文件没有丢，它在 feature/banner 所指的提交里。' },

      out: 'Updating 15f1190..c0cd205\nFast-forward\n banner.py | 1 +\n 1 file changed, 1 insertion(+)\n create mode 100644 banner.py',
      note: 'Fast-forward：main 没有自己的新提交，Git 只是把 main 挪到了 c0cd205。',
    },
    { cmd: 'ls', out: 'banner.py  portcheck.py  README.md  secret.txt' },
    {
      cmd: 'git log --oneline --graph --all',
      out: '* c0cd205 (HEAD -> main, feature/banner) Add banner\n* 15f1190 Add README and ignore secrets\n* 4f5d1a3 Print done at the end\n* 91ee7f5 Add port check script',
      note: '两条分支现在指着同一个提交。没有多出新提交。',
    },

/>

`git merge 分支名` 的方向是：把那条分支**合并进当前所在的分支**。所以合并之前先切到接收改动的分支上。

<Callout variant="warning" title="解决冲突之后先运行一遍">
Git 只检查你有没有 `git add`，不检查文件内容对不对。冲突标记如果没删干净就提交了，`<<<<<<< HEAD` 这样的行会留在代码里，脚本一运行就是 SyntaxError。提交之前先把程序跑一遍。
</Callout>

## 三、远程仓库与社团的协作流程

### 1. 把仓库推到远程

到目前为止，全部历史都只在你这台虚拟机上。**远程仓库**（remote）是放在别处的同一个项目，大家把自己的提交推送上去，再从它那里取回别人的提交。社团的远程仓库在 GitHub 上。

这一节不需要账号和网络：在本机建一个目录充当远程仓库，命令和连接 GitHub 时完全相同，只有地址不同。

<TerminalSession
  title="建一个远程仓库，把 main 推上去"
  steps={[
    { cmd: 'git init --bare ~/lab/remote.git', out: 'Initialized empty Git repository in /home/kali/lab/remote.git/', note: '--bare 建的是裸仓库：只存历史，没有工作区，专门用来接收推送和被克隆。' },
    { cmd: 'git remote add origin ~/lab/remote.git', note: '给当前仓库登记一个远程仓库，简称 origin。连接 GitHub 时，最后一个参数换成仓库的网址。' },
    { cmd: 'git remote -v', out: 'origin\t/home/kali/lab/remote.git (fetch)\norigin\t/home/kali/lab/remote.git (push)' },
    {
      cmd: 'git push -u origin main',
      out: "…（前面几行是打包和传输的进度，数字因机器而异，这里省略）\nTo /home/kali/lab/remote.git\n * [new branch]      main -> main\nbranch 'main' set up to track 'origin/main'.",
      note: '把 main 推送到 origin。-u 让本地的 main 记住它对应远程的 main，以后在这条分支上只敲 git push、git pull 就行。',
    },
    { cmd: 'git status', out: "On branch main\nYour branch is up to date with 'origin/main'.\n\nnothing to commit, working tree clean", note: 'status 多了一行：本地的 main 和远程的 main 一致。' },
  ]}
/>

`origin` 只是一个约定俗成的简称。`origin/main` 是 Git 在本地记下的「远程仓库的 main 上次在哪」。（来源：[Pro Git: Working with Remotes](#source-progit-remotes)、[git-push](#source-git-push)、[gitglossary](#source-gitglossary)）

### 2. 队友克隆、提交、推送，你拉取

再克隆一份到另一个目录，假装它是队友的电脑。

<TerminalSession
  title="扮演队友：clone，提交，push"
  steps={[

/>

<TerminalSession
  title="回到自己的仓库：pull"
  steps={[

      out: '…（传输进度省略）\nFrom /home/kali/lab/remote\n   a294e73..97587a5  main       -> origin/main\nUpdating a294e73..97587a5\nFast-forward\n ping.py | 1 +\n 1 file changed, 1 insertion(+)\n create mode 100644 ping.py',
      note: 'pull 做了两件事：取回远程的新提交，再把它们合并进当前分支。你没有自己的新提交，所以是快进。',
    },
    { cmd: 'ls', out: 'banner.py  ping.py  portcheck.py  README.md  secret.txt' },
    { cmd: 'git log --oneline -3', out: '97587a5 (HEAD -> main, origin/main, origin/HEAD) Add ping script\na294e73 Merge feature/title\n43ebdb9 Capitalize the title', note: '-3 只看最近三个提交。' },
  ]}
/>

如果你和队友都直接在 `main` 上提交并推送，后推送的人会被拒绝，必须先把对方的提交取回来合并，才能再推。人一多，这种情况会不断发生。社团的做法是谁也不直接往 `main` 上推。

### 3. 社团的流程：同仓分支 + PR

每一项改动都在自己的分支上做，推送这条分支，然后在 GitHub 上发起一个 **pull request**（PR）：一份「请把这条分支合并进 main」的提议。其他人在网页上看你改了什么、提意见，通过之后才合并。（来源：[About pull requests](#source-github-pull-requests)）

先在本地把你这一侧的动作走一遍：

<TerminalSession
  title="在分支上改，推送这条分支"
  steps={[

    { cmd: 'git add README.md' },
    { cmd: 'git commit -m "Document how to run"', out: '[docs/usage cec13d0] Document how to run\n 1 file changed, 1 insertion(+)' },
    {
      cmd: 'git push -u origin docs/usage',
      out: "…（传输进度省略）\nTo /home/kali/lab/remote.git\n * [new branch]      docs/usage -> docs/usage\nbranch 'docs/usage' set up to track 'origin/docs/usage'.",
      note: '推送的是 docs/usage 这条分支。远程的 main 没有被动过。',
    },
    { cmd: 'git switch main', out: "Switched to branch 'main'\nYour branch is up to date with 'origin/main'.", note: '回到 main。本地练习到这里为止。' },
  ]}
/>

边界：`git push` 有一个 `--force` 选项，可以用本地的历史强行覆盖远程的历史，别人已经推送的提交会因此消失。被拒绝时的正确做法是先 pull，不是强推。在多人共用的分支上不要使用它。（来源：[git-push](#source-git-push)）

<KeyTakeaway>
分支是指向某个提交的名字，HEAD 记着你在哪条分支上。在分支上提交不影响其他分支，`git merge` 把一条分支并入当前分支：能快进就只挪指针，分叉了就生成合并提交，改了同一处就停下来等你解决。协作时每项改动走自己的分支，推送分支，经 PR 审查后再合并进 main。
</KeyTakeaway>
