## 引导问题：为什么一段好 Prompt 最后会长成一套系统

拿一个真实的研发杂活贯穿整节课：**发版前，让 AI 自动读一遍本周代码提交和未关闭的阻断 Bug，写一份带编号出处的发布简报，发现高危问题时标出来，但「点击发布」必须留给人批准。**

你会发现，光靠在对话框里写一段漂亮 Prompt 远远不够：模型看不到你刚推上去的新代码，得接数据源；聊天聊长了会把关键 Bug 挤出注意力，得管上下文；模型可能漏写风险却信誓旦旦说「可以发版」，得靠代码写死外部检查；碰到发布按钮绝不能让它自己点，得在外面加权限闸门。

于是工程对象一层层往外长出来，一共七层：

<StepList title="七层并存：从写指令到画执行图" steps={engineeringLayers} />

先破一个常见误解：**这七层不是「新版本淘汰旧版本」的替代关系，而是同时跑在同一个系统里的七种零件。** 哪怕搭了最复杂的执行图，图里每个节点依然要写清晰的 Prompt，依然受同一个 Harness 管权限和预算。

## 一、Prompt Engineering：先把需求写成能验收的规格

### 1. 少喊口号，多写边界和契约

很多新手写 Prompt 喜欢堆情绪词（「你是世界顶级专家，请务必认真仔细」），效果微乎其微。模型读不懂你心里的潜台词，它只吃你喂进去的文字。Anthropic 官方指南把顺序说得很明白：**先定成功标准和测试用例，再去调 Prompt；碰到模型能力、延迟或成本问题，该换模型换模型，别指望靠改词句变魔术**（来源：[Prompt engineering overview](#source-anthropic-prompt-overview)）。

## 二、MCP：给外部工具装上统一插座

以前每接一个新模型应用，查 GitHub、读数据库、发消息都得重写一遍胶水代码。**MCP（Model Context Protocol）**干的事就像 USB-C 接口：定义一套开放协议，让 **Host**（你的 AI 应用）通过 **Client** 连上各种 **MCP Server**，用标准的 JSON-RPC 消息自动发现并调用外部能力（来源：[MCP architecture overview](#source-mcp-architecture)）。

    ["Tools", "模型可以请求执行的函数", "查询合并提交、拉取阻断 Issue", "结构化 JSON 或报错"],
  ]}
/>

设计工具时，**工具名称、描述和 JSON Schema 本身就是给模型看的 API 文档**。下面把一个宽泛查询收窄成只查 `release-blocker`，参数越明确，模型乱传参的概率越低：

```json
{
  "name": "list_release_issues",
  "description": "读取指定仓库中尚未关闭的发布阻断项",
  "inputSchema": {
    "type": "object",
    "properties": {
      "repository": { "type": "string" },
      "label": { "const": "release-blocker" }
    },
    "required": ["repository", "label"],
    "additionalProperties": false
  }
}
```

<Callout variant="warning" title="接上 MCP 不等于自动安全">
MCP 规范明确提醒：Tools 可能读取敏感数据甚至执行任意代码，不可信 Server 返回的工具描述本身也可能是恶意诱导（来源：[MCP Tools specification](#source-mcp-tools-spec)）。协议只负责「怎么连、怎么叫」，至于「当前用户有没有权读这个库」「高危工具要不要弹人工确认」，依然必须由 Host 和 Harness 的代码强控。
</Callout>

## 三、Skills：把团队老手的办事流程打包复用

光有工具还不够：哪怕给了你「查提交」「查 Issue」「发通知」三个按钮，新人还是不知道先按哪个、遇到冲突怎么裁决。**Agent Skill** 就是把一套反复要做的流程，连同参考文档、模板和确定性脚本，打包成一个以 `SKILL.md` 为入口的可移植目录（来源：[Agent Skills Specification](#source-agent-skills-spec)）：

```text
release-brief/
├── SKILL.md                 ← 入口说明：什么时候用、按哪几步走
├── references/
│   └── release-policy.md    ← 长规范按需读，平时不塞进窗口
├── assets/
│   └── brief-template.md    ← 输出模板
└── scripts/
    └── normalize-version.js ← 确定性逻辑交给脚本，别让模型口算
```

Skill 的妙处在于**渐进式加载**：启动时只把几十个 token 的名称和简介放进窗口；真碰上对口任务，才读 `SKILL.md` 正文；走到具体步骤需要查大规范或跑脚本时，再按需加载，极省上下文预算：

<SkillLoading />

一份清爽的流程型 `SKILL.md` 长这样：

```md
---
name: release-brief
description: 根据提交、Issue 和里程碑生成发布简报。需要进展总结或发布风险排查时使用。
---

1. 读取本次版本的已合并提交。
2. 获取仍未关闭的 release-blocker Issue。
3. 将结果分为「已完成」「风险」「待决策」。
4. 每项风险附对应来源编号；缺少证据时写 unknown，不推测。
5. 输出前检查版本范围、重复项和未解决阻断项。
```

一句话分清 **MCP 和 Skill**（来源：[OpenAI Skills](#source-openai-skills)）：**MCP 管「手脚怎么连上外部系统、怎么鉴权」；Skill 管「拿到工具后按什么步骤干活、缺材料怎么兜底、交什么格式」**。两者可以单独用，也可以搭档用。

## 四、Context Engineering：每一轮只喂最值钱的信息

### 1. 窗口是动态变脏的，不是一次性写死的

模型每次推理实际看到的全部 token 统称 **Context（上下文）**——系统规则、对话历史、工具定义、检索片段、工具返回的大段日志全挤在同一个有限窗口里（来源：[Effective context engineering for AI agents](#source-anthropic-context-engineering)）。

在多步任务里，窗口不是静态的，而是随着工具一轮轮调用迅速变满、变脏。点下面 6 个阶段，亲眼看看一个正常任务怎么在第 4 步被冗长日志撑爆、又怎么靠压缩和重排救回来：

## 五、Harness Engineering：把模型关进靠谱的工作间

哪怕给顶尖厨师配齐食材和菜单，如果厨房没火候表、没验菜标准、煤气灶还没安全阀，照样会翻车。包在模型外面的那整套工程底座——负责拼上下文、管工具、存状态、卡权限、跑外部检查、设预算和录日志——在行业里常被称为 **Agent Harness**（注：业界对 framework、runtime、harness 的叫法仍有重叠，这里把它当作便于拆解系统的工作定义，来源：[LangChain Harness Boundaries](#source-langchain-harness-boundaries)）。

OpenAI 的 Harness Engineering 工程实践也分享了一条非常实在的经验（来源：[OpenAI Harness Engineering](#source-openai-harness-engineering)）：**别把所有规矩全塞进一个几千行的超大说明文档里**，而是留一份简短的入口地图，把规范拆成仓库里可版本化维护的文档，并尽量把「口头叮嘱」升级成 **lint、类型检查和 CI 自动测试**——代码自动拦住的坑，远比在 Prompt 里重复叮嘱十遍稳得多。

## 六、Loop Engineering：让模型看真实反馈、撞预算就停

### 1. 有界反馈循环怎么跑

早期的 ReAct 论文把「思考 → 调工具 → 看外部观察 → 修正下一步」串成了一个经典循环（来源：[ReAct](#source-react-paper)）：

<StepList title="可收敛的 Agent 内环" steps={agentLoopSteps} />

把视角拉高一点，LangChain 把工程里的反馈循环分成了四类（属于近期实践框架，方便定位问题发生在哪，来源：[The Art of Loop Engineering](#source-langchain-loop-engineering)）：**Agent Loop**（单次任务里边做边看工具返回）、**Verification Loop**（跑完测试不通过就打回去修）、**Event-driven Loop**（由定时任务或 Webhook 触发执行）、**Hill-climbing Loop**（利用生产轨迹和失败模式，经人工确认与回归评测后持续改进 Prompt、工具或 Harness 配置）。

不管哪层循环，控制器里必须写死**停机和恢复规则**：瞬时网络超时走有界退避 **Retry**；方案验证失败把报错证据喂回去 **Replan**；等人工审批先落盘 **Resume**；出了副作用要能 **Rollback**；撞上步数/成本上限果断 **失败停止** 并汇报现场证据，绝不让 Agent 无限空转。

### 2. 别信模型自述，把「轨迹」和「结果」分开验

Anthropic 在 Agent 评测文章里强调了一点：**过程轨迹（Trace）和最终环境状态（Outcome）必须分开检查**（来源：[Demystifying evals for AI agents](#source-anthropic-agent-evals)）。模型完全可能在文字里写着「所有检查已通过」，但磁盘上的文件根本没改对。

## 七、Graph Engineering：何时才需要把流程画成执行图

当任务不再是单线循环，而是出现「先并行查安全、文档、兼容性三条线，全部汇合后再写草稿，校验不过打回重写，过了还得等人工审批」时，就需要把执行结构显式画成一张**执行图**（注：「Graph Engineering」是 2026 年夏季在社区集中流行的说法，主流框架各自叫 state graph、graph-based workflow 等，但底层的状态机与有向图编排都很成熟，来源：[原帖与讨论存档](#source-graph-origin-archive)、[LangGraph Graph API](#source-langgraph-graph-api)）。

## 常见误区与工程边界

- **别把模型自述当完成证据**：成功条件必须写成外部确定性检查（测试、Schema 校验、数据库状态），不看模型嘴上怎么说。
- **别把多 Agent 当银弹**：每多加一个节点和子代理，都会成倍增加 token 费用、状态同步难度和排障复杂度；没有评测数据证明收益就别加。
- **别忘了最小权限和硬预算**：无论图画得多漂亮，最大步数、超时时间和写操作审批门必须写在模型外面的代码里。

这一课我们把「一个任务怎么可控地跑完」拆透了。接下来把镜头再拉远，进入第五课《AI 工程全景：从一次调用到生产系统》：看看线上生产系统除了编排之外，还要怎么配 RAG 检索、分层记忆、微调蒸馏、评测护栏、可观测性和成本网关。

<KeyTakeaway>
Agent 工程不是玄学，而是把一次聊天一步步变成可控软件：用 **Prompt** 写清规格，用 **MCP** 接外部工具，用 **Skills** 复用流程，用 **Context** 精选每轮输入，用 **Harness** 管住权限、预算和外部校验，用 **Loop** 吸收真实反馈并有界收敛，只在分支并行真的复杂到管不过来时才上 **Graph**。
</KeyTakeaway>
