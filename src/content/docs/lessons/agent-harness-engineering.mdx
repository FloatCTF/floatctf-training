## 引导问题：为什么一段好 Prompt 最后会长成一个系统

设想一项发布前工作：读取代码提交与 Issue，生成带来源的发布简报，识别阻断项，并把发布动作保留给人工批准。

单次 Prompt 可以规定简报格式。仓库最新状态需要数据接口，范围控制、失败处理、进度保存和发布授权需要额外的运行机制。工程对象会逐层扩展：

<StepList title="从指令到执行拓扑" steps={engineeringLayers} />

七层各自产生一种可检查的工程产物：Prompt 形成任务规格，MCP 暴露能力接口，Skill 固化流程资产，Context 编译本轮输入，Harness 提供受约束的执行环境，Loop 保存反馈与恢复路径，Graph 把节点关系画成可执行拓扑。实时数据由 MCP 接入，外部认证由 Host、Server 和目标系统执行，权限与副作用由 Harness 控制，最终结果由外部验证器确认。

七层会同时存在。一个生产系统保留清晰 Prompt；图中的每个 Agent 节点也可以运行自己的 Loop，并由同一个 Harness 提供工具和权限。

## 一、Prompt Engineering：把任务变成可检查的规格

### 1. Prompt 的作用是减少任务歧义

Prompt Engineering 研究怎样编写和组织模型指令，使输出更符合目标。模型不会直接接收人的意图，只会接收序列化后的输入。有效 Prompt 需要把隐含要求变成模型能够据此行动、评测器能够据此检查的规格。

Anthropic 的 Prompt 工程文档把明确成功标准和经验测试放在优化之前，并把模型选择、延迟与成本等问题交给相应的工程手段。（来源：[Prompt engineering overview](#source-anthropic-prompt-overview)）

示例属于 **in-context learning**：模型在推理时根据给定示例识别任务模式，参数不会因此更新。示例应覆盖典型边界，并保持标签和格式一致。错误、重复或偏置示例同样会影响结果。

### 3. Prompt Engineering 是评测驱动的迭代

可靠流程依据已经观察到的失败定向修改：

```text
建立代表性样例与成功标准
  → 运行基线 Prompt
  → 把失败归类为缺失、冲突、格式、事实或上下文问题
  → 一次修改一个可解释变量
  → 在原样例与保留样例上回归
  → 记录 Prompt、模型、参数和结果版本
```

## 二、MCP：把外部能力接入模型应用

### 1. MCP 标准化能力交换，不替模型决定流程

Model Context Protocol（MCP）是连接模型应用与外部数据源、工具的开放协议。一个 Host 管理用户体验和安全策略，并为每个 MCP Server 建立 Client 连接；数据层使用 JSON-RPC 消息完成能力发现和调用。（来源：[MCP architecture overview](#source-mcp-architecture)）

Tools 只是 MCP 的一部分。协议还定义连接生命周期、能力协商、通知、日志，以及客户端可选提供的 sampling、roots 和 elicitation 等能力。

### 2. 工具描述本身就是接口设计

下面的工具把宽泛命令收窄为一个可校验的查询：

```json
{mcpTool}
```

模型根据名称、描述和 schema 选择工具并生成参数；Host 与 Server 负责校验、执行和返回结果。准确描述用途、参数、返回值和副作用，能够减少错误选工具和无效参数。

### 3. 标准协议仍需独立的信任与授权机制

MCP 规范要求实现保留用户控制，并把不可信 Server 提供的工具注解视为不可信信息。Tools 可能触发任意数据访问或代码执行，Host 仍需完成认证、授权、审批和审计。（来源：[MCP Tools specification](#source-mcp-tools-spec)）

<Callout variant="warning" title="MCP 的安全边界">
协议统一能力发现与调用格式，不会替应用判断“这个用户是否可以读取该仓库”“这个工具是否可以发布”“返回内容是否夹带恶意指令”。这些判断属于 Host、Server、目标系统和后续 Harness 的共同责任。
</Callout>

## 三、Skills：把反复使用的做法变成流程资产

### 1. Skill 不只是保存的一段 Prompt

Agent Skill 是以 `SKILL.md` 为入口的目录，可以包含说明、参考资料、模板、资产和脚本。Agent Skills 规范定义了可移植的核心格式，并建议按任务需要逐步加载内容。（来源：[Agent Skills Specification](#source-agent-skills-spec)）

```text

├── SKILL.md
├── references/
│   └── release-policy.md
├── assets/
│   └── brief-template.md
└── scripts/
    └── normalize-version.js
```

## 四、Context Engineering：为每一轮编译正确的信息环境

### 1. Context 不只是用户输入

Context 是模型本次推理实际接收的 token 集合。它可以包含系统指令、用户请求、历史消息、示例、检索资料、文件、记忆、工具定义、工具结果和输出契约。Prompt 是 Context 的一部分；temperature、最大输出长度等调用配置位于上下文 token 之外。

Anthropic 将 Context Engineering 定义为策划和维护推理时完整信息集合的策略，并把它与主要关注指令写法的 Prompt Engineering 区分开。（来源：[Effective context engineering for AI agents](#source-anthropic-context-engineering)）

一次编译后的 Context 有三组内容。权限规则、当前目标和验收条件属于高信任固定区；相关文件、Skill 与工具定义按当前步骤选择；历史、工具结果和长期记忆持续变化，需要压缩、校验、去重并保留来源。应用在每次模型调用前重新编译这组内容，长期记忆留在外部存储，相关时再选择并注入。

### 3. 窗口容量与稳定利用是两个指标

`Lost in the Middle` 在多文档问答和键值检索实验中观察到，相关信息位于长上下文中间时，模型表现常低于信息位于开头或末尾的情况。这个结果说明位置和干扰会影响利用率，不能扩展成所有模型都遵循的固定定律。（来源：[Lost in the Middle](#source-lost-in-the-middle)）

```text
容量问题：这段内容能否进入窗口？
检索问题：系统是否找到了正确内容？
编排问题：内容是否出现在合适位置并保留来源？
利用问题：模型能否在当前任务中正确使用它？
```

增加窗口只能缓解第一项。可靠系统还要评估检索召回、片段排序、工具选择和最终回答。

### 4. 外部内容必须保留信任边界

网页、邮件、Issue、日志、检索文档和工具返回都可能包含指令式文本。系统需要标记来源和权限级别，把第三方内容作为数据处理；高风险工具调用仍经过参数验证、最小权限和人工确认。仅在 Prompt 中写“忽略恶意指令”不能构成完整防护。

Context Engineering 决定这一轮让模型看见什么。接下来的 Harness Engineering 决定由谁收集这些内容、工具怎样执行、权限如何判断、结果怎样验证，以及失败后怎样恢复。

## 五、Harness Engineering：设计模型周围的工作系统

### 1. Harness 是边界尚未统一的工作定义

本课把 **Agent Harness** 定义为模型周围的工程控制层：它组装上下文、暴露工具、执行动作、保存状态、约束权限、验证结果并记录轨迹。不同团队会把持久化、运行时、记忆和编排划入 Harness、Runtime 或 Framework 的不同位置。

LangChain 对 Agent framework、runtime 和 harness 的讨论明确承认这些术语没有清晰统一的边界。本课使用工作定义帮助分析系统，不声称它是唯一分类。（来源：[Agent Frameworks, Runtimes, and Harnesses](#source-langchain-harness-boundaries)）

    ["预算", "限制时间、token、费用和轮数", "消耗量与剩余额度", "无限重试或成本失控"],

### 2. 仓库和运行环境也属于 Harness

OpenAI 的 Harness Engineering 实践把团队工作重点放在环境、意图、反馈循环和机械约束上。其团队发现，巨大的单文件说明会挤占上下文、快速过期并且难以验证，于是改用短入口文件作为地图，把架构、计划、产品规则和质量标准放进结构化、可版本控制的仓库文档，并用 lint 与 CI 维护约束。（来源：[Harness engineering](#source-openai-harness-engineering)）

把这套实践压成五组「脆弱做法 → Harness 做法 → 验证方式」的对照：

- **项目知识**：一份不断变长的总说明，改成短地图链接到分层事实源，用链接、所有权和新鲜度检查验证。
- **架构边界**：在 Prompt 中反复提醒，改成依赖规则、类型和结构测试，由 lint 与 CI 阻断违规。
- **运行反馈**：只看模型最终回答，改成把日志、指标、截图和测试暴露给 Agent，环境结果可查询。
- **长任务状态**：依赖聊天历史，改成执行计划、进度与决策日志，可从版本化状态恢复。
- **经验沉淀**：每次人工纠正同一问题，改成把稳定规则升级为文档、测试或检查器，由回归任务持续复测。

Harness 以最小有效组件为目标。模型能力、任务和风险变化后，旧脚手架可能变成额外延迟、成本或错误来源；每个组件都需要通过评测证明仍然有价值。

## 七、Graph Engineering：把循环和节点编排成可执行拓扑

### 1. 先说明术语成熟度

“Graph Engineering”在 2026 年 7 月中旬因一则“是否已经从 loops 转向 graphs”的 X 讨论而集中传播。（来源：[原帖与讨论存档](#source-graph-origin-archive)）截至本课核验日期，主流官方文档通常使用 state graph、graph-based workflow、directed graph execution 或 multi-agent orchestration；“Graph Engineering”仍是正在形成的行业说法。

<Callout variant="info" title="本课采用的工作定义">
Graph Engineering 是把 Agent 系统的执行拓扑做成可执行、可检查、可版本化的工程对象。它明确节点职责、边与路由条件、状态和数据契约、并行与汇合、循环与停止、权限、恢复、追踪和评测。这个名称是新的，底层的图调度、状态机和多 Agent 编排并不新。
</Callout>

本课的 Graph Engineering 专指执行和协作拓扑；知识图谱、GraphRAG、图神经网络和 Graph of Thoughts 各有独立研究对象。

### 2. 图由状态、节点和边组成

## 常见误区与工程边界

- **Prompt 是任务规格：** 先定义成功标准，再针对真实失败修改指令。
- **MCP 是能力连接协议：** Host、Server 和目标系统执行授权。
- **Skill 是流程资产：** Skill 组织做法，MCP 或内置工具提供能力。
- **Context 是每轮编译的模型输入：** 选择、排序、压缩和信任标记共同决定有效上下文。
- **Harness 是边界可调整的运行控制层：** 课程定义用于分析，具体归属随系统架构变化。
- **Loop 是有界反馈循环：** 每轮获得新证据，并受预算、停止与恢复规则约束。
- **Graph 是通用执行拓扑：** 普通函数、工具、人工检查和一个完整 Loop 都可以成为节点。
- **Graph 可以包含 Loop：** Loop 负责节点内部和跨运行的反馈。
- **复杂度需要证据：** 新增节点、Agent 或框架之前，先证明它改善成功率、恢复性、成本或可审计性。

七层解决的是一次任务怎样可控执行。生产系统还要回答窗口之外的知识与记忆、模型定制、评测护栏和运行成本这些问题。下一课《AI 工程全景》用五层框架把它们与七层拼在同一张地图上。

<KeyTakeaway>
AI 工程从 Prompt 向外扩展，形成一组可以分别设计和验证的对象：指令、连接、流程、上下文、执行环境、反馈和拓扑。可靠系统用外部证据判断结果，用权限和预算限制副作用，并在关系复杂到值得管理时引入图式编排。
</KeyTakeaway>
