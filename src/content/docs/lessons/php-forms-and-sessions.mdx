## 引导问题：把第 14 课的练习站翻过来

第 14 课的 `server.py` 里，登录是这样实现的：把表单正文拆开，和一个写在代码里的密码比较，对了就生成一个随机编号，放进 `Set-Cookie`，同时在服务器的字典里记下「这个编号是 student」。

每一步都是手写的。PHP 把其中大部分做成了现成的：表单数据已经拆好放在 `$_POST` 里，会话编号的生成、发送、读取都由 `session_start()` 完成。你要做的，是在正确的地方做正确的检查。

### 3. 为什么一定要转义

<CodeFile file="labs/php-forms-and-sessions/raw.php" note="同一个输入，一行直接输出，一行转义后输出。" />

<TerminalSession
  title="终端 B：输入里带着 HTML 标签"
  steps={[
    {
      cmd: "curl -s 'http://127.0.0.1:8000/raw.php?name=%3Cb%3Ekali%3C%2Fb%3E'",
      out: '<p>raw:     <b>kali</b></p>\n<p>escaped: &lt;b&gt;kali&lt;/b&gt;</p>',
      note: '%3C 和 %3E 是第 4 课讲过的 URL 编码，代表 < 和 >。用户提交的是 <b>kali</b>。',
    },
  ]}
/>

用浏览器打开同一个网址：第一行的 kali 是**粗体**，因为浏览器把用户输入里的 `<b>` 当成了标签；第二行原样显示 `<b>kali</b>` 这几个字符。

这就是问题所在：**不转义时，用户输入的内容会变成页面的一部分 HTML。** 这里只是一个加粗标签，无伤大雅；但用户能写进页面的绝不只是加粗。第 17 课讲过，页面里的脚本可以读写整个 DOM、带着 Cookie 发请求。下学期的 XSS 一课会专门讲这件事的后果。

`htmlspecialchars` 把 `<`、`>`、`&`、引号换成 HTML 实体，浏览器就只把它们当作字符显示。PHP 手册的入门教程里也是这样写的：它让人无法往你的页面里注入 HTML 标签或 JavaScript。（来源：[Dealing with Forms](#source-php-forms)、[htmlspecialchars](#source-php-htmlspecialchars)）

<Callout variant="warning" title="规矩">
凡是来自请求的数据，`$_GET`、`$_POST`、`$_COOKIE`，以及以后从数据库里读出来的、最初由用户写进去的内容，放进 HTML 之前一律经过 `htmlspecialchars`。没有例外。
</Callout>

### 1. Cookie

<TerminalSession
  title="终端 B：设置和读取 Cookie"
  steps={[
    {

      out: 'HTTP/1.1 200 OK\nHost: 127.0.0.1:8000\nDate: Fri, 02 Oct 2026 14:06:09 GMT\nConnection: close\nX-Powered-By: PHP/8.4.24\nSet-Cookie: theme=dark\nContent-type: text/html; charset=UTF-8\n\ntheme saved',
      note: 'setcookie 生成的就是第 14 课见过的 Set-Cookie 响应头。',
    },
    { cmd: "curl -b 'theme=dark' http://127.0.0.1:8000/theme.php", out: 'theme: dark', note: '请求里带着 Cookie，PHP 把它放进 $_COOKIE。' },
    { cmd: 'curl http://127.0.0.1:8000/theme.php', out: 'theme: light' },
  ]}
/>

`setcookie` 是在设置响应头，所以必须在任何输出之前调用，包括 `<html>` 这样的 HTML 和空白。（来源：[setcookie](#source-php-setcookie)）

注意第二条命令：Cookie 的值是你自己在命令行里写的。浏览器这一侧想写什么都行。所以 Cookie 适合存「主题偏好」这种改了也无所谓的东西，**不能用来存「我是谁」**。

## 三、一个完整的登录

### 1. 密码不存明文

<CodeFile file="labs/php-forms-and-sessions/make_hash.php" />

<TerminalSession
  title="终端 B：生成和核对密码散列"
  steps={[
    { cmd: 'php make_hash.php', out: '$2y$12$6n02eUnn.gDHzBLyiXYSauw4xOkiWD7BzI8gMFrkrhwzeIeoaIr0W\nbool(true)\nbool(false)', note: '每次运行散列都不同，因为每次都随机加了盐。但 password_verify 都认得它。' },
  ]}
/>

数据库或文件里只存 `password_hash` 生成的散列，登录时用 `password_verify` 核对。散列是单向的：从它算不回原来的密码。即使存密码的文件被人拿走，拿到的也不是密码本身。散列开头的 `$2y$12$` 说明了算法（bcrypt）和代价，后面跟着随机的盐和结果，核对需要的信息都在这一串里。（来源：[password_hash](#source-php-password-hash)、[password_verify](#source-php-password-verify)）

边界：这一课的写法够用于学习，离真实网站还差几件事：会话 Cookie 应当加上 `HttpOnly` 和 `SameSite` 属性（`session_start` 可以传参数设置）；表单应当防止别的网站代替用户提交；登录失败的次数应当有限制。这些下学期在对应的漏洞专题里讲。

<KeyTakeaway>
表单数据在 `$_GET` 或 `$_POST` 里，放进页面之前一律用 `htmlspecialchars` 转义。Cookie 存在客户端，任何人都能改，只适合存无关紧要的偏好。会话把数据留在服务器上，客户端只拿一个随机编号，`session_start()` 之后通过 `$_SESSION` 读写。密码只存 `password_hash` 的散列，用 `password_verify` 核对；登录成功后用 `session_regenerate_id` 换号。
</KeyTakeaway>
